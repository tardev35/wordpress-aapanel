## 11.1b 👀 บอทมันทำอะไรบ้าง — ดูด้วยตาตัวเอง

บอทที่เจาะ `bbc29pro.com` **ไม่ได้ทำอะไรซับซ้อนกว่า 2 ขั้นนี้เลย**

### ขั้นที่ 1 — หารายชื่อโดเมนใหม่ทั้งโลก

เปิด [crt.sh](https://crt.sh) แล้วค้นโดเมนของเราดู — ข้อมูลนี้เปิดสาธารณะ
ใครก็ดึงได้ และมี API ให้ดึงเป็น JSON แบบอัตโนมัติด้วย

```
https://crt.sh/?q=โดเมนของเรา&output=json
```

ผลของ `bbc29pro.com` ที่ดึงมาจริง: **มี 4 ใบ ใบแรกขึ้น log ตอน 14:57 ของวันที่ออก cert**

ไม่ต้องสแกน IP ไม่ต้องรอ Google — **รายชื่อถูกแจกให้ฟรีอยู่แล้ว**

### ขั้นที่ 2 — ยิง path มาตรฐานดูว่าอันไหนตอบ

นี่คือทั้งหมดที่มันทำ ไม่มีอะไรมากกว่านี้:

```bash
curl -s https://โดเมน/wp-includes/wlwmanifest.xml   # เป็น WordPress ไหม
curl -s https://โดเมน/wp-json/wp/v2/users           # ชื่อผู้ใช้
curl -s https://โดเมน/readme.html                   # เวอร์ชันอะไร
curl -s https://โดเมน/.env                          # มีของหลุดไหม
curl -s https://โดเมน/xmlrpc.php                    # ประตูเดารหัส
```

**อันไหนตอบ 200 = ช่องที่ใช้ต่อได้** ที่เหลือคือเอาไปเข้าเครื่องมือสำเร็จรูปต่อ

### ตรวจเว็บตัวเองและเว็บเพื่อนได้เลย

[`scripts/check-exposure.sh`](../scripts/check-exposure.sh) ทำขั้นที่ 2 ให้ดู
**มันแค่เปิดหน้าเว็บสาธารณะแล้วดูว่าตอบอะไร ไม่ได้เจาะอะไรทั้งนั้น**

```bash
bash check-exposure.sh example.com          # เว็บที่ไหนก็ได้ ไม่ต้องอยู่บนเครื่องเรา
ssh root@SERVER_IP "bash /root/wpaa/scripts/check-exposure.sh"   # ทุกไซต์บนเครื่อง
```

ผลจริงของ `neda88-pro.com` **หลัง**ติดตั้งเกราะแล้ว:

```
/xmlrpc.php                403  ปิดแล้ว   เดารหัสผ่านรัว ๆ
/wp-json/wp/v2/users       401  ปิดแล้ว   แจกชื่อผู้ใช้
/readme.html               403  ปิดแล้ว   บอกเวอร์ชัน
/wp-config.php             403  ปิดแล้ว   รหัสผ่านฐานข้อมูล
/.env  /.git/config        404  ไม่มี/ปิด
meta generator             -    เปิดอยู่  WordPress 6.5.10   <-- ยังเหลือ
```

**ก่อน**ติดตั้ง `/wp-json/wp/v2/users` ตอบ `200` พร้อมข้อมูลนี้:

```json
[{"id":2,"name":"admin 789mybet","slug":"admin", ...}]
```

**ชื่อผู้ใช้คือ `admin`** — การเดารหัสผ่านต้องใช้ 2 อย่างคือชื่อผู้ใช้กับรหัสผ่าน
ถ้าชื่อผู้ใช้แจกฟรี งานของบอทเหลือครึ่งเดียว และ `admin` คือชื่อที่มันเดาก่อนอยู่แล้ว

> ### สิ่งที่ยังเหลือ: `meta generator` บอกเวอร์ชัน
> `<meta name="generator" content="WordPress 6.5.10" />` อยู่ในหน้าเว็บ ไม่ใช่ที่ nginx
> จึงบล็อกด้วยกฎ nginx ไม่ได้ ต้องปิดจากฝั่ง WordPress
>
> **ทำไมสำคัญ:** บอทเอาเวอร์ชันไปเทียบกับรายการช่องโหว่ แล้วเลือกยิงเฉพาะตัวที่ตรงรุ่น
> — เครื่องนี้ปิด auto-update ไว้ ([08 ADR-012](08-decisions.md)) เวอร์ชันจึงค้างที่เดิม
> และ**ยิ่งค้างนาน ยิ่งมีช่องโหว่ที่ประกาศแล้วตรงรุ่นมากขึ้น**

## 11.1c 📡 บอทดึงรายชื่อโดเมนจากที่ไหน

ทั้งหมดนี้เป็นโครงสร้างพื้นฐานสาธารณะ ไม่ใช่ของใต้ดิน — **มีไว้เพื่อความโปร่งใส**
แต่ผลข้างเคียงคือใครก็ได้รายชื่อโดเมนใหม่ทั้งโลกฟรี ๆ

| แหล่ง | คืออะไร | ได้อะไร |
|---|---|---|
| **CT log servers ตรง ๆ** | เซิร์ฟเวอร์ append-only ที่ CA ต้องส่ง cert เข้าไป — Google (Argon/Xenon), Cloudflare (Nimbus), Let's Encrypt (Oak), DigiCert, Sectigo · มี HTTP API ให้ดึงทีละช่วง | **ทุกใบที่ออกทั้งโลก** |
| **certstream** ⭐ | รวม CT log ทุกตัวที่ Chrome/Apple เชื่อถือ แล้วสตรีมออกทาง WebSocket · ฟรี · มีไลบรารี Python / Go / JS | **เรียลไทม์ ทุกใบทั้งโลก** |
| [crt.sh](https://crt.sh) | หน้าค้นหา + API JSON ของ Sectigo | ค้นย้อนหลังทีละโดเมน |
| Censys · Shodan · SecurityTrails · urlscan.io | ทำ index ของ CT + การสแกนไว้ให้ ค้นแบบมีเงื่อนไขได้ | มีทั้งฟรีและเสียเงิน |
| **ICANN CZDS** | ไฟล์ zone ของ TLD — ขอสิทธิ์แล้วโหลดได้ · รายชื่อ **.com ทั้งหมด** อัปเดตรายวัน | ทุกโดเมนที่จดใน TLD นั้น |
| NRD feed เชิงพาณิชย์ | รายชื่อโดเมนที่เพิ่งจด ขายเป็นรายเดือน | โดเมนใหม่ทั้งหมด |

**ตัวที่ทำให้บอทมาถึงใน 58 นาทีคือ certstream** — มันไม่ต้องรอ zone file รายวัน
เพราะ cert ถูกสตรีมออกมาภายในไม่กี่วินาทีหลังออก และเชื่อมได้ด้วยโค้ดไม่กี่บรรทัด

ต่างกันตรงนี้:

- **zone file** บอกว่า "โดเมนนี้ถูกจดแล้ว" — แต่ยังไม่มีเว็บ ยิงไปก็ไม่เจออะไร
- **CT log** บอกว่า "โดเมนนี้ออก cert แล้ว" = **มีเว็บจริงพร้อมให้ยิงแล้ว**

จึงเป็นเหตุผลที่ CT คือแหล่งที่บอทเลือกใช้ ไม่ใช่ zone file

### 🔴 นัยที่สำคัญกับเรา: เกราะต้องพร้อม "ก่อน" ขอ cert

ลำดับที่ออกแบบไว้:

```
กด Add site  ->  watcher stamp ให้ใน ~1 วินาที (ใส่ 01-hardening.conf)
                 ...ทีมค่อยไปกด SSL ทีหลัง
                 cert ออก -> โลกรู้ -> บอทมาถึงใน ~1 ชม.
```

**เกราะควรติดตั้งเสร็จก่อน cert ออก** เพราะ `stamp-site.sh` ทำงานตอน Add site
ไม่ใช่ตอนขอ SSL — ถ้าวันไหนมีคนย้ายลำดับ หรือปิด watcher ช่องว่างนี้จะเปิดทันที

> ⚠️ **ยังไม่ได้พิสูจน์กับไซต์ใหม่จริง** — ไซต์ทั้งหมดบนเครื่องได้เกราะแบบย้อนหลัง
> (ติดตั้ง 29 ส.ค. ส่วน cert ออกก่อนหน้านั้น) ต้องรอไซต์ถัดไปที่ทีมสร้าง
> แล้วเทียบเวลา `01-hardening.conf` กับ `notBefore` ของ cert ถึงจะยืนยันได้
>
> ```bash
> D=DOMAIN.TLD
> stat -c 'hardening %y' /www/server/panel/vhost/nginx/extension/$D/01-hardening.conf
> openssl x509 -in /www/server/panel/vhost/cert/$D/fullchain.pem -noout -startdate
> ```

### เอาไปใช้ฝั่งเราบ้าง: เฝ้า cert ของตัวเอง

ข้อมูลชุดเดียวกันใช้ป้องกันได้ — **ถ้ามีใครออก cert ให้โดเมนเราโดยที่เราไม่ได้ขอ
เราจะรู้ทันที** (สัญญาณว่าโดเมนหรือ DNS ถูกยึด)

- **Cloudflare** → SSL/TLS → มี Certificate Transparency Monitoring ให้เปิดต่อ zone
- [crt.sh](https://crt.sh) มี RSS ต่อโดเมน สมัครรับแจ้งเตือนได้
- Google เปิด CT monitoring ให้เจ้าของโดเมนเช่นกัน

> ⚠️ **การเฝ้าไม่ได้ทำให้ซ่อนตัวได้** มันแค่ทำให้เรารู้เท่าที่คนอื่นรู้
> การป้องกันจริงยังเป็นข้อเดียวเดิม: **ปิดช่องให้หมดก่อนเว็บขึ้น**

GET /glaucodot/h5i8t8h3e2r8m9o3s4t5/
GET /?d=a5g3n3u1s0501001

ไซต์ถูกใช้ยิงหน้าเว็บปลอมเพื่อดันอันดับให้เว็บอื่น — เจ้าของเว็บมักไม่รู้ตัวเพราะหน้าแรก
ยังปกติดีทุกอย่าง

### ทางเข้าที่น่าจะเป็น

`fileorganizer` 1.2.0 — **ปลั๊กอินจัดการไฟล์** ซึ่งโดยธรรมชาติมีความสามารถอ่าน/เขียนไฟล์
ทั้งไซต์อยู่แล้ว ถ้ามีช่องโหว่สิทธิ์ ผู้บุกรุกได้ทุกอย่างทันที

> ⚠️ **ไม่ได้ยืนยัน 100% ว่าเป็นตัวนี้** — ไม่มี log ของ PHP ย้อนหลังพอจะชี้ชัด
> แต่มันเป็นปลั๊กอินเดียวในไซต์ที่มีความสามารถเขียนไฟล์ และไทม์ไลน์สอดคล้อง
> **ปลั๊กอิน file manager ไม่ควรอยู่บนเว็บ production เลย** — ใช้ SFTP แทน

## 11.3 เกราะที่ติดตั้งแล้ว

[`scripts/harden-wp.sh`](../scripts/harden-wp.sh) + [`configs/wp-hardening.conf`](../configs/wp-hardening.conf)

```powershell
ssh root@SERVER_IP "bash /root/wpaa/scripts/harden-wp.sh --check"   # ดูก่อน
ssh root@SERVER_IP "bash /root/wpaa/scripts/harden-wp.sh"           # ติดตั้ง
ssh root@SERVER_IP "bash /root/wpaa/scripts/harden-wp.sh --remove"  # ถอดออก
```

| กฎ | ปิดอะไร | ทดสอบได้ว่า |
|---|---|---|
| `xmlrpc.php` → 403 | brute force ผ่าน `system.multicall` ที่ลองรหัสได้หลายร้อยครั้งต่อ request | `403` |
| ห้ามรัน PHP ใน `wp-content/uploads/` | ปลายทางของช่องโหว่ upload แทบทุกตัว | `403` |
| ห้ามเรียก PHP ใน `wp-includes/` ตรง ๆ | ทางที่เชลล์ `x9d5285/index.php` ถูกเรียก | `403` |
| บล็อกโฟลเดอร์/ไฟล์ซ่อน (`/.`) | ทางที่ซ่อน `.well-known/.<md5>system/` | `404` |
| บล็อก `wp-config.php`, `.sql`, `.env`, `.bak` | ไฟล์ที่ไม่ควรหลุด | `403` |
| `/wp-json/wp/v2/users` → 401 | แจกชื่อผู้ใช้ให้บอท (ทดสอบแล้วได้ `admin` กลับมาจริง) | `401` |
| `/?author=1` → 403 | ทางเก่าที่ให้ชื่อผู้ใช้เหมือนกัน | `404` |
| จำกัด `wp-login.php` 5 ครั้ง/นาที/IP | brute force หน้า login | — |
| **ยกเว้น** `.well-known/acme-challenge/` | ถ้าบล็อกด้วย **SSL จะต่ออายุไม่ผ่าน** | `200` |

**ไซต์ใหม่ได้เองอัตโนมัติ** — [`stamp-site.sh`](../scripts/stamp-site.sh) ทำ symlink ให้
ตอนสร้างไซต์ ซึ่ง watcher เรียกอยู่แล้ว ([05 §5.1c](05-operations.md))

`verify-config.sh` มีด่าน **`กฎกันแฮ็ก (01-hardening)`** ตรวจว่าทุกไซต์ได้ครบ

### 🔴 กฎพวกนี้ไม่ได้แทนการอัปเดต

มันทำให้**ของที่เจาะเข้ามาแล้วเอาไปใช้ต่อไม่ได้** และซื้อเวลา
แต่ถ้าปลั๊กอินมีช่องโหว่ ทางเข้ายังเปิดอยู่

และเครื่องนี้ **ปิด auto-update ของ WordPress ไว้ทั้งหมด** ([08 ADR-012](08-decisions.md))
งาน "อัปเดต WP + ปลั๊กอินทุกสัปดาห์" จึงเป็น **ห้ามพลาด** ไม่ใช่ควรทำ

## 11.4 วิธีตรวจว่าไซต์ติดหรือยัง

รันได้ทุกเมื่อ ไม่แตะอะไร:

```bash
# 1. ลายเซ็น .htaccess ของผู้บุกรุก (ตัวชี้ที่แม่นที่สุด)
grep -rl "suspected" /www/wwwroot/ --include=".htaccess" 2>/dev/null \
  | sed 's|/www/wwwroot/||;s|/.*||' | sort -u

# 2. ไฟล์ PHP ที่ถูก obfuscate ด้วย goto
grep -rlE '<\?php goto [A-Za-z0-9]+;' /www/wwwroot/ --include='*.php' 2>/dev/null

# 3. โฟลเดอร์ซ่อนที่ไม่ใช่ acme-challenge
find /www/wwwroot -type d -path "*/.well-known/*" 2>/dev/null | grep -v acme-challenge

# 4. บัญชี admin ที่ไม่ควรมี (ทำทีละไซต์)
cd /www/wwwroot/DOMAIN
DB=$(grep -m1 DB_NAME wp-config.php|sed "s/.*'DB_NAME', *'//;s/'.*//")
DU=$(grep -m1 DB_USER wp-config.php|sed "s/.*'DB_USER', *'//;s/'.*//")
DP=$(grep -m1 DB_PASSWORD wp-config.php|sed "s/.*'DB_PASSWORD', *'//;s/'.*//")
PFX=$(grep -m1 table_prefix wp-config.php|sed "s/.*= *'//;s/'.*//")
mysql -u"$DU" -p"$DP" "$DB" -e "SELECT ID,user_login,user_email,user_registered FROM ${PFX}users;"
```

**ตรวจข้อ 4 ทุกครั้งที่สงสัย** — ไฟล์ลบได้ แต่ถ้าบัญชีปลอมยังอยู่ เขาเดินกลับเข้าประตูหน้า

## 11.5 ถ้าติดแล้วทำยังไง

### ลำดับที่ทำจริงในเคสนี้

1. **หยุดสิ่งที่กินเครื่องก่อน** — บล็อก `xmlrpc.php` ทั้งเครื่อง
   CPU ลงจาก **92% เหลือ idle 99%** ทันทีหลัง reload
2. **ย้ายไฟล์อันตรายออกจาก web root** — `mv` ไม่ใช่ `rm`
   เก็บไว้ที่ `/root/wpaa/quarantine/<domain>-<เวลา>/` เป็นหลักฐาน
3. **ปิดบัญชีปลอม** — dump ตาราง `users`/`usermeta` เก็บไว้ก่อน แล้วถอดสิทธิ์
   (ไม่ลบแถว เพื่อไม่ให้เนื้อหาที่ผูกกับ user เป็นกำพร้า)
4. **ถอดปลั๊กอินที่น่าจะเป็นทางเข้า**
5. **ติดตั้งเกราะให้ทุกไซต์** ไม่ใช่แค่ไซต์ที่ติด

### 🔴 แต่ทั้งหมดนี้ยัง "ไม่สะอาด"

ไซต์ที่เคยถูกยึด **ไม่มีใครรับประกันได้ว่าเจอครบ** ผู้บุกรุกอาจฝังโค้ดไว้ในธีม
ในฐานข้อมูล ในตาราง options หรือใน cron ของ WordPress เอง

**ทางที่ปลอดภัยจริงคือสร้างไซต์ใหม่แล้วย้ายเฉพาะเนื้อหา** (โพสต์ + รูป) ไม่ยกไฟล์เดิมมา

การทำความสะอาดหน้างานคือการ **ซื้อเวลา** ไม่ใช่การแก้จบ — ต้องบอกเจ้าของเว็บตามจริง
