## 5.1b งานที่ทำอัตโนมัติทุกคืน 🤖

**ติดตั้งครั้งเดียว แล้วไม่ต้องมานั่งรันเองทุกวัน**

### 🕐 กับดักเรื่องเวลา — อ่านก่อนตั้ง ไม่ว่าจะตั้งวิธีไหน

**เครื่องนี้ตั้ง timezone เป็น UTC** (`timedatectl` → `Etc/UTC`) ดังนั้น:

```
23:00 เวลาไทย  =  16:00 บนเครื่อง
```

**หน้า Cron ของ aaPanel ก็ใช้เวลาเครื่อง ไม่ใช่เวลาไทย** — หลักฐานจากงานที่มีอยู่แล้วบนเครื่องนี้:
หน้าเว็บแสดงว่ารันตอน `8:46` และในไฟล์ `crontab` คือ `46 8 * * *` ตรงกันเป๊ะ

**ใส่ `23:00` ตรง ๆ ไม่ว่าที่ไหน = ไปรัน 6 โมงเช้าของวันถัดไปตามเวลาไทย**

### ทาง A: หน้า Cron ของ aaPanel ⭐ แนะนำ

ทีม**มองเห็นและกดดูเองได้** ทั้งสถานะ เวลารันล่าสุด และ log — ต่างจากบรรทัดใน `crontab`
ที่ไม่โผล่ในหน้า panel เลย

คัดลอกไฟล์ขึ้นเครื่องก่อน โดยสั่งไม่ให้มันไปแตะ crontab:

```powershell
scp -r configs scripts root@SERVER_IP:/tmp/wpaa/
ssh root@SERVER_IP "bash /tmp/wpaa/scripts/install-autoheal.sh --no-cron"
```

แล้วไป **aaPanel → Cron Job → Add Task**:

| ช่อง | ค่า |
|---|---|
| Task type | **Shell Script** |
| Task name | `wpaa nightly check` |
| Execute cycle | **Daily** · `16` : `00` ← **16 ไม่ใช่ 23** |
| Execute user | **root** |
| Script content | `/root/wpaa/scripts/nightly-check.sh` |

ช่อง Script content ใส่แค่บรรทัดเดียวเรียกสคริปต์ — **อย่าก๊อปเนื้อสคริปต์มาวาง**
ไม่งั้นจะมีโค้ดสองชุดให้ต้องไล่แก้ตามกันทุกครั้งที่อัปเดต repo

### ทาง B: crontab ตรง ๆ

```powershell
ssh root@SERVER_IP "bash /tmp/wpaa/scripts/install-autoheal.sh"
```

ใส่เป็น `0 16 * * *` พร้อม `flock` กันรันซ้อน · ถอดออกด้วย:

```powershell
ssh root@SERVER_IP "bash /tmp/wpaa/scripts/install-autoheal.sh --remove-cron"
```

> ⚠️ **เลือกทางเดียว** ถ้าเคยตั้งทาง B แล้วจะย้ายไปทาง A ต้องถอดของเดิมออกก่อน
> ไม่งั้นรันวันละ 2 รอบ — เช็คด้วย `crontab -l | grep wpaa`
>
> เกิดขึ้นจริงบน `187.52.125.203` (ตั้งไว้ทั้งสองทางพร้อมกัน) แก้แล้วเมื่อ 2026-08-25
> โดยเลือก **ทาง B** ส่วนงานในหน้า Cron ของ panel ถูกปิดไว้ (`status = 0`) ไม่ได้ลบทิ้ง
> ตรวจว่าเครื่องไหนเป็นแบบไหนได้จาก `crontab -l | grep -c nightly-check` — ต้องได้ `1`
>
> ตั้งใจไม่ใช้ `CRON_TZ=Asia/Bangkok` (ซึ่งจะทำให้เขียน 23:00 ได้ตรง ๆ) เพราะ `CRON_TZ`
> มีผลกับ **ทุกบรรทัดที่อยู่ถัดจากมัน** ในไฟล์เดียวกัน จะไปเลื่อนเวลางาน cron ของ aaPanel
> ที่อยู่ในไฟล์นั้นด้วยโดยไม่มีใครรู้

### สิ่งที่มันทำทุกคืน

| ตรวจ | ถ้าเจอปัญหา |
|---|---|
| `enable-php-83-wpfastcgi.conf` ถูก WP Toolkit เขียนทับ | กู้ฉบับที่จูนแล้วกลับ + ล้าง cache |
| `0.catchall_ssl.conf` หาย | ติดตั้งกลับ |
| ไซต์ที่ยังไม่ได้ stamp (ไม่มี `00-common.conf`) | ใส่กฎกลางให้ |
| ไซต์ใหม่ที่ auto-update ยังเปิดอยู่ | ใส่ `AUTOMATIC_UPDATER_DISABLED` (ตรวจ `php -l` ก่อนทับ) |
| ไซต์ที่ปุ่ม Purge ใช้ไม่ได้ (ปลั๊กอินหาย/ปิด/ค่าเพี้ยน) | เรียก `fix-cache-purge.sh` ครบทั้ง 5 ข้อ ([04 §4.7](04-cache.md)) |
| `/etc/my.cnf` ถูก panel เขียนทับ | ตั้งค่ากลับ **แล้ว restart MariaDB** ([03 §3.4](03-tuning.md)) |

> 🔴 **แถวสุดท้ายคือข้อเดียวที่ restart service** ข้ออื่นแค่ reload nginx
> ยอมรับได้เพราะรอบนี้ยิงตอน 23:00 และวัดจริงได้ 2–3 วินาทีบนเครื่อง 145 ไซต์
> หน้าที่อยู่ใน FastCGI cache ไม่กระทบเลยเพราะไม่แตะ PHP/MySQL
>
> ทำไมต้องมี: หน้า Databases → Performance tuning ของ panel เขียนทับ `my.cnf` ทั้งไฟล์
> ค่าที่ตั้งไว้ 25 ส.ค. ถอยกลับหมดทั้ง 2 เครื่องภายใน 2 วัน โดยไม่มีอะไรฟ้อง

> 🔴 **เพราะ auto-update ถูกปิด งาน "อัปเดต WP ทุกสัปดาห์" ในตารางข้างบนจึงเปลี่ยนจาก
> "ควรทำ" เป็น "ห้ามพลาด"** — ไม่มีอะไรมาแพตช์ช่องโหว่ให้แล้ว ดู [08 ADR-012](08-decisions.md)

**มันแก้ให้เลย ไม่ใช่แค่รายงาน** เพราะวิธีแก้คือเอาไฟล์ที่รู้ว่าถูกไปทับ ซึ่งไม่ต้องใช้วิจารณญาณ
แต่จะแตะเฉพาะตอนที่ต่างจริง และ **`nginx -t` ก่อน reload เสมอ** ถ้าไม่ผ่านจะไม่ reload
ของเดิมยังวิ่งอยู่และเขียนลง log ไว้ให้เข้าไปดู

### 🔴 มันคือตาข่ายนิรภัย ไม่ใช่ตัวแทนของ `stamp-site.sh`

ถ้าเพิ่มเว็บตอน 10 โมงแล้วรอให้ cron 5 ทุ่มมาเก็บกวาด **โดเมนนั้นจะเสิร์ฟเว็บของลูกค้าคนอื่น
อยู่ 13 ชั่วโมง** และ FastCGI cache จะเก็บหน้าผิดนั้นไว้ตลอดช่วงเวลานั้นด้วย
(ดู [04 §4.5](04-cache.md)) — **ยังต้องรัน `stamp-site.sh` ทันทีหลัง Add site เหมือนเดิม**
cron มีไว้จับกรณีที่คนลืม ไม่ได้มีไว้ให้ตั้งใจลืม

### ✅ ทดสอบว่ามันซ่อมได้จริงแล้ว (2026-08-23)

รันเฉย ๆ แล้วได้ `[ok] ไม่มีอะไรเปลี่ยน` **ยังไม่นับว่าทดสอบ** — มันพิสูจน์แค่ทางที่ไม่มีอะไรผิด
หลักเดียวกับ backup ที่ไม่เคย restore ก็ยังไม่นับว่าเป็น backup

จึงทำให้พังจริงแล้วดูว่ามันกู้กลับ:

| ทำให้พัง | ผล |
|---|---|
| ลบ symlink `00-common.conf` ของไซต์หนึ่งทิ้ง | ตรวจเจอ → สร้างกลับ → `nginx -t` → reload |
| เติมบรรทัดเข้าไปใน `enable-php-83-wpfastcgi.conf` ให้ต่างจากต้นฉบับ | ตรวจเจอ → สำรองฉบับที่เพี้ยนไว้ → กู้ต้นฉบับกลับ → reload → **ล้าง cache 59 ไฟล์เหลือ 0** |

หลังทดสอบ: ทุกโดเมนยังเสิร์ฟเว็บตัวเอง · โดเมนแปลกหน้ายังได้ 404 · `X-Cache: HIT` กลับมาทันที

**ทดสอบซ้ำเองได้ทุกเมื่อ** (ปลอดภัย เพราะสคริปต์สำรองก่อนทับเสมอ):

```bash
# จำลองว่า WP Toolkit มาเขียนทับ
echo "# test" >> /www/server/nginx/conf/enable-php-83-wpfastcgi.conf
/root/wpaa/scripts/nightly-check.sh
tail -5 /var/log/wpaa-nightly.log
```

## 5.1c ไซต์ใหม่ถูก stamp ให้เอง ไม่ต้องมีใครสั่ง 🤖

ตั้งครั้งเดียวต่อเครื่อง:

```powershell
scp -r configs scripts root@SERVER_IP:/tmp/wpaa/
ssh root@SERVER_IP "bash /tmp/wpaa/scripts/install-site-watcher.sh"
```

หลังจากนี้ **ทีมงานกด Add site ในแผงอย่างเดียวจบ** ไม่ต้องเปิด cmd ไม่ต้อง ssh
ถอดออกด้วย `install-site-watcher.sh --remove`

ได้ systemd unit 2 ตัวที่เรียก [`watch-new-sites.sh`](../scripts/watch-new-sites.sh) ตัวเดียวกัน:

| unit | ตื่นเมื่อ | หน้าที่ |
|---|---|---|
| `wpaa-newsite.path` | panel เขียนไฟล์ลง `vhost/nginx/` = **วินาทีที่กด Add site** | reload nginx ให้ทันที ก่อนใครจะเปิดโดเมนทัน |
| `wpaa-newsite.timer` | ทุก 1 นาที | ตาข่าย + เป็นตัวที่ปิด auto-update เพราะ `wp-config.php` โผล่มาทีหลัง |

**ต้องมีทั้งคู่** — `path` unit เฝ้าโฟลเดอร์ `vhost/nginx/` ซึ่งเปลี่ยนตอนสร้างไซต์ แต่
`wp-config.php` ของ WordPress ไปโผล่**ข้างใน** `/www/wwwroot/<domain>/` ซึ่งไม่ทำให้
โฟลเดอร์ที่เฝ้าอยู่เปลี่ยน `path` unit จึงมองไม่เห็น ต้องให้ timer เก็บ

> ### 🔴 เคยล้างแคชทั้งเครื่อง แล้วมันกัดจริงเมื่อ 2026-08-28
>
> รุ่นแรกของ watcher ล้าง FastCGI cache **ทั้งเครื่อง** ทุกครั้งที่กู้ config
> เวลา 00:55 UTC ทีมเพิ่มไซต์ตอนที่มีทราฟฟิก ~50,000 request/ชั่วโมง
> แคชของ 145 ไซต์หายพร้อมกัน ทุก request จึงวิ่งเข้า PHP
> **PHP-FPM เต็ม 35 worker แล้ว load พุ่งเป็น 11.95 บนเครื่อง 4 cores**
> (ยืนยันจากไฟล์แคชทุกไฟล์มี timestamp เดียวกันคือ 00:55:32)
>
> แก้เป็น **ล้างเฉพาะไฟล์ที่เกิดหลังจากเวลาที่ config ถูกเขียนทับ** — ช่วงที่กฎผิดจริง ๆ
> สั้นแค่ไม่กี่วินาทีถึงหนึ่งนาที ของที่แคชไว้ก่อนหน้านั้นยังถูกต้องอยู่แล้ว
> ทดสอบแล้ว: **ล้าง 9 ไฟล์ เหลือ 1369** เทียบกับเดิมที่จะล้างทั้ง 1378 ไฟล์

### ทำไมรอบกลางคืนอย่างเดียวไม่พอ

`login-edo89.com` บนเครื่อง `187.52.125.203` — **ลง `6.7.7` ถูกต้องตามที่เลือก** แต่:

| เวลาไทย | เกิดอะไร |
|---|---|
| 00:04 | panel สร้างไซต์ ลง WordPress `6.7.7` |
| 00:07 | เขียน `wp-config.php` — ยังไม่มี `AUTOMATIC_UPDATER_DISABLED` เพราะไม่ได้รัน `stamp-site.sh` |
| **01:08** | **WordPress อัปตัวเองเป็น `7.1`** — ห่างจากติดตั้งแค่ **1 ชั่วโมง** |
| 23:00 | `nightly-check.sh` เพิ่งจะมาถึง = **สายไป 22 ชั่วโมง** |

ตาข่ายที่ตาห่างกว่าความเร็วของสิ่งที่จะจับ ไม่ได้จับอะไรเลย งานนี้จึงยิงทุกนาที
ช่องว่างระหว่าง "กด Add site" กับ "ถูก stamp" จึงเหลือไม่เกิน 1 นาที

### มันตัดสินใจจากอะไร

**ไม่มีไฟล์จำสถานะ** — อ่านจากของจริงทุกรอบว่าไซต์ไหนยังขาดอะไร จึงกู้ตัวเองได้ทั้งกรณีที่
panel เขียนทับ และกรณีที่เครื่องดับกลางคัน

| เจอ | ทำ |
|---|---|
| `enable-php-83-wpfastcgi.conf` ต่างจากต้นฉบับใน `/root/wpaa/configs/` | สำรอง กู้ฉบับที่จูนแล้วกลับ reload แล้วล้างแคชทั้งเครื่อง — **ถ้า `nginx -t` ไม่ผ่านจะเอาของเดิมกลับ** |
| โฟลเดอร์ใน `/www/wwwroot/` ที่**ไม่มี** `vhost/nginx/<domain>.conf` | ข้าม — ไม่ใช่ไซต์ที่ panel สร้าง |
| ไซต์ที่ไม่มี `extension/<domain>/00-common.conf` | รัน `stamp-site.sh` (กฎ www + ปิด auto-update + reload) แล้วล้างแคชของโดเมนนั้น |
| ไซต์ WordPress ที่ `.user.ini` ยังไม่มี path ของโฟลเดอร์แคชใน `open_basedir` | รัน `fix-cache-purge.sh <domain>` — ไม่งั้นปุ่ม Purge ในหน้า WP กดแล้วเงียบ ([04 §4.7](04-cache.md)) |
| ไซต์ที่ stamp แล้ว แต่ `wp-config.php` ยังไม่มี `AUTOMATIC_UPDATER_DISABLED` | รัน `set-wp-autoupdate.sh` อย่างเดียว **ไม่ reload nginx ซ้ำ** |

แถวสุดท้ายไม่ใช่เคสหายาก — มันคือ **ลำดับปกติ** ของ WP Toolkit ที่สร้าง vhost ก่อนแล้วค่อย
เขียน `wp-config.php` ทีหลัง รอบแรก watcher จึง stamp ตอนที่ยังไม่มี WordPress ให้ปิด
แล้วมาปิดให้ในรอบถัดไป

> (ลบทิ้งหลังทดสอบแล้ว)

### ดู log

### 🔴 `path` unit ตายเงียบได้ด้วย `unit-start-limit-hit`

systemd จำกัดจำนวนครั้งที่ service ถูกสตาร์ทไว้ (default 5 ครั้งใน 10 วินาที)
`path` unit ยิง service ทุกครั้งที่มีอะไรเปลี่ยนใน `vhost/nginx/` ซึ่งตอน panel ต่ออายุ SSL
หรือทีมเพิ่มไซต์รัว ๆ จะเปลี่ยนหลายครั้งติดกัน → เต็มโควตา → **systemd ฆ่า path unit ทิ้ง**

เกิดจริงบน `187.52.122.249` เมื่อ 2026-08-27 18:25 UTC และ **ตายอยู่ 7 ชั่วโมง**
กว่าจะรู้ตอน `verify-config.sh` ฟ้อง — ระหว่างนั้น timer รอบนาทียังทำงาน ไซต์ใหม่จึงยัง
ถูก stamp อยู่ แค่ช้าลงจากเสี้ยววินาทีเป็นไม่เกิน 1 นาที

แก้ด้วย `StartLimitIntervalSec=0` ใน service unit (มีใน
[`install-site-watcher.sh`](../scripts/install-site-watcher.sh) แล้ว)
ถ้าเจอ unit ที่ `failed` อยู่:

```bash
systemctl reset-failed wpaa-newsite.path
bash /root/wpaa/scripts/install-site-watcher.sh
```

```bash
systemctl status wpaa-newsite.path           # ต้องเป็น active (waiting)
systemctl list-timers wpaa-newsite.timer     # รอบล่าสุด / รอบถัดไป
journalctl -u wpaa-newsite.service -n 50
tail -30 /var/log/wpaa-newsite.log
```

> log **เขียนเฉพาะรอบที่มีอะไรให้แก้จริง** เพราะยิงทุกนาที ถ้าเขียนทุกรอบจะได้วันละ
> 1440 บรรทัดที่ไม่มีข้อมูลอะไรเลย — **log ว่างแปลว่าไม่มีไซต์ไหนหลุด ไม่ใช่ว่ามันไม่ทำงาน**
> เช็คว่ามันยังเป็นอยู่ด้วย `systemctl list-timers` แทน

### แล้วความเสี่ยงเรื่อง FastCGI cache ที่เคยเตือนไว้ล่ะ

เคสที่เคยเจอ (ดู [07 ข้อ 10–11](07-troubleshooting.md)) คือโดเมนที่ nginx ยังไม่รู้จักตกไปที่
default server แล้ว HTML ของเว็บลูกค้าอีกรายถูกเก็บใต้คีย์ของโดเมนใหม่ ค้าง 1 วัน

**เคสนั้นถูกปิดไปแล้วตั้งแต่ [ADR-011](08-decisions.md)** ตรวจซ้ำบนเครื่องแล้วเมื่อ 2026-08-25:

```
curl -sk --resolve nosuch.invalid:443:127.0.0.1 https://nosuch.invalid/   -> 404
grep -c fastcgi_pass /www/server/panel/vhost/nginx/0.catchall_ssl.conf    -> 0
```

catch-all `return 404` ตรงจาก nginx **ไม่มี `fastcgi_pass` เลย** จึงป้อน FastCGI cache
ไม่ได้ตั้งแต่ต้น และ `fastcgi_cache_valid` ก็เก็บเฉพาะ 200/301/302 อยู่แล้ว
ช่วงก่อน reload คนที่เปิดโดเมนใหม่จึงได้ **404 ชั่วคราว** ไม่ใช่เว็บของคนอื่น

`watch-new-sites.sh` ยังสั่งล้างแคชของโดเมนนั้นหลัง stamp อยู่ดี เป็นชั้นกันเผื่อวันที่
catch-all หลุดหาย (ซึ่ง `nightly-check.sh` จะติดตั้งกลับให้ แต่ไม่เกินคืนนั้น)

### 🔴 `stamp-site.sh` ยังมีไว้ทำไม

ไว้ให้คนที่กำลัง**แก้ปัญหาเฉพาะหน้า**เรียกเอง และเป็นตัวงานที่ watcher เรียกใช้
**ขั้นตอนปกติหลัง Add site ไม่ต้องเรียกมันแล้ว**

## 5.1e cron บนเครื่องนี้มีอะไรบ้าง

ตรวจเมื่อ 2026-08-23 — **มีแค่ 2 งาน** ทั้งคู่เปิดอยู่ (`status = 1`)

| งาน | เวลา | ทำอะไร | ปิดได้ไหม |
|---|---|---|---|
| `Domain SSL Renew Let's Encrypt Certificate` | 08:46 UTC | ต่ออายุ SSL ทุกโดเมน (`acme_v2.py --renew_v3=1`) | 🔴 **ห้ามปิด** |
| `wpaa nightly check` | 16:00 UTC (= 23:00 ไทย) | ตรวจ+ซ่อม config, ปิด auto-update ไซต์ใหม่ | ปิดได้แต่ไม่ควร |

### 🔴 อย่าปิดงาน 08:46 เด็ดขาด

มันคือตัวต่ออายุใบรับรอง Let's Encrypt ของทุกโดเมนบนเครื่อง ใบรับรองมีอายุ 90 วัน
**ปิดแล้วจะไม่มีอะไรพังทันที** — แต่ประมาณสองเดือนถัดมาเว็บทั้งเครื่องจะขึ้นเตือน
"ใบรับรองหมดอายุ" พร้อมกัน ซึ่งเป็นความพังชนิดที่ตอนเกิดจะนึกไม่ออกแล้วว่ามาจากการกดปิดวันนี้

### ไม่มี cron ไหนอัปเดต WordPress

ยืนยัน 3 ทาง:

```bash
crontab -l                                    # มี 2 บรรทัด ตามตารางข้างบน
grep -rl "wp-cron\|wordpress" /etc/cron.d /etc/cron.daily /etc/crontab   # ว่าง
grep -c "auto_update\|automatic_update" /www/server/panel/class_v2/wp_toolkit/core.py   # 0
```

**WP Toolkit ไม่มีระบบ auto-update ของตัวเอง** — ตัวที่อัป WordPress ขึ้น 7.1 คือ
**wp-cron ของ WordPress เอง** ซึ่งทำงานตอนมีคนเข้าเว็บ ไม่ได้อยู่ใน crontab ของเครื่อง
จึงหาไม่เจอในหน้า Cron ของ panel

ปิดไปแล้วด้วย `AUTOMATIC_UPDATER_DISABLED` ใน `wp-config.php` ทุกไซต์
([08 ADR-012](08-decisions.md)) — **ไม่ต้องไปปิด cron ตัวไหนเพิ่ม**

> 📌 ยังไม่ได้ปิด `wp-cron` ทั้งตัว (`DISABLE_WP_CRON`) ตาม §5.5 นะ ซึ่งคนละเรื่องกัน:
> `AUTOMATIC_UPDATER_DISABLED` ห้ามมันอัปเดต ส่วน `DISABLE_WP_CRON` ห้ามมันทำงานตอนมี
> คนเข้าเว็บ (เพื่อลดภาระเมื่อมีเว็บเยอะ) — ข้อหลังยังอยู่ในรายการค้าง

## 5.2 ⚠️ หลังอัปเดต aaPanel ทุกครั้ง

**การอัปเดตอาจเขียนทับไฟล์ที่เราแก้เอง** (สังเกตว่าไฟล์ `enable-php-*` ตัวอื่นลงวันที่จากตัวติดตั้ง)

### สคริปต์ตรวจ

```bash
ssh root@SERVER_IP "bash -s" < scripts/verify-config.sh
```

> 📌 **รอบ 2026-08-23 สคริปต์นี้จับ drift ได้จริง** — รายงานว่าเครื่องอ้างอิง ไม่มี `fastcgi_cache_lock`,
> ไม่มี `use_stale`, ยังมี `Cache-Control: max-age=0` และ Redis ไม่มี `maxmemory`
> ทั้งที่เอกสารรุ่นแรกเขียนเหมือนทำครบแล้วทุกข้อ
>
> บทเรียน: **"เขียนไว้ในเอกสาร" กับ "ทำแล้วบนเครื่อง" เป็นคนละเรื่อง** และต่างกันได้ตั้งแต่วันแรก
> ไม่ใช่แค่ตอนอัปเดต panel เขียนทับ — ให้รันสคริปต์นี้ตอนรับเครื่องใหม่มาดูแลด้วย ไม่ใช่เฉพาะหลังอัปเดต

หรือตรวจด้วยมือ:

```bash
# FastCGI cache config
grep -c "fastcgi_cache_lock" /www/server/nginx/conf/enable-php-83-wpfastcgi.conf
# ได้ 0 = โดนเขียนทับ → กู้จาก .bak-*

# PHP-FPM
grep -E "^pm |^pm\.max_children" /www/server/php/83/etc/php-fpm.conf
# ต้องได้ ondemand / 35

# MySQL
mysql -uroot -p -e "SHOW VARIABLES LIKE 'innodb_buffer_pool_size';"
# ต้องได้ 4294967296
```

### ไฟล์ที่ต้องเฝ้าระวัง

| ไฟล์ | ความเสี่ยง |
|---|---|
| `/www/server/nginx/conf/enable-php-83-wpfastcgi.conf` | **สูง** — WP Toolkit เขียนทับได้ |
| `/www/server/php/83/etc/php-fpm.conf` | ปานกลาง |
| `/www/server/php/83/etc/php.ini` | ปานกลาง |
| `/etc/my.cnf` | ต่ำ |
| `/etc/sysctl.d/99-tuning.conf` | ต่ำ (ไม่ใช่ของ aaPanel) |

## 5.3 Backup 🔴

> **สถานะปัจจุบัน: ยังไม่ได้ตั้ง — นี่คืองานที่เร่งด่วนที่สุด**
> เว็บ production ที่ไม่มี backup = ถ้าพัง ข้อมูลหายถาวร

### หลักการ 3-2-1

- **3** สำเนา
- **2** สื่อที่ต่างกัน
- **1** อยู่นอกสถานที่ (offsite)

### ชั้นที่ 1 — Hostinger VPS Backup (มีอยู่แล้ว)

- อัตโนมัติ **รายสัปดาห์** ฟรี เก็บสูงสุด 4 ชุด
- เก็บแยกจากเซิร์ฟเวอร์ ไม่หักโควตาดิสก์
- **ไม่สามารถเปลี่ยนเวลาได้**

### ⚠️ ข้อจำกัดของ Snapshot

- **เก็บได้ครั้งละ 1 ชุดเท่านั้น** — สร้างใหม่จะเขียนทับของเดิม
- **หมดอายุใน 1 วัน**
- **ถูกลบถ้าติดตั้ง OS ใหม่หรือ restore จาก backup**

**แปลว่า snapshot ใช้เป็นตาข่ายชั่วคราวระหว่างทำงานวันนั้นเท่านั้น ไม่ใช่ backup จริง**

### ชั้นที่ 2 — aaPanel → Offsite (ต้องตั้ง)

**aaPanel → Cron → Add task**

| ช่อง | ค่า |
|---|---|
| Type | Backup site / Backup database |
| Schedule | ทุกวัน 03:00 |
| Backup to | **S3-compatible** (Backblaze B2 / Cloudflare R2) |
| Keep | 7 ชุด |

**ค่าใช้จ่าย:** ~200 GB ≈ **฿600/ปี**
เทียบกับ Hostinger daily backup add-on ฿419/เดือน = ฿5,028/ปี → **ต่างกัน 8 เท่า**

### 🔴 ข้อที่ห้ามข้าม

> **หลังตั้ง backup เสร็จ ต้อง restore จริง 1 เว็บทันที**
> **backup ที่ไม่เคยกู้คืนสำเร็จ ยังไม่นับว่าเป็น backup**

## 5.4 SMTP ภายนอก 🔴

**อย่าให้ WordPress ส่งอีเมลจาก VPS โดยตรง** — IP ใหม่ไม่มีชื่อเสียง เมลจะเข้า spam
หรือถูกปฏิเสธ (ผู้ให้บริการอีเมลปฏิเสธเมลจาก IP ที่ forward/reverse DNS ไม่ตรงกัน)

### ติดตั้งทุกเว็บ

ปลั๊กอิน **WP Mail SMTP** → ชี้ไปบริการภายนอก

| บริการ | ฟรี | เหมาะกับ |
|---|---|---|
| Brevo | 300 เมล/วัน | ทีมเล็ก, ฟอร์มติดต่อ |
| Amazon SES | ~$0.10/1,000 | ปริมาณเยอะ ถูกที่สุด |
| Resend | 3,000/เดือน | ตั้งค่าง่ายที่สุด |

**ตั้ง SPF, DKIM, DMARC ใน DNS ของ Cloudflare ด้วย**

## 5.5 wp-cron

**ปิด wp-cron ในตัว** — ถ้าปล่อยไว้ 100 เว็บจะทริกเกอร์ cron ทุกครั้งที่มีคนเข้า

`wp-config.php`:
```php
define('DISABLE_WP_CRON', true);
define('WP_POST_REVISIONS', 5);
define('EMPTY_TRASH_DAYS', 14);
define('AUTOSAVE_INTERVAL', 120);
```

**ตั้ง system cron แทน — กระจายเวลาไม่ให้ยิงพร้อมกัน:**

```
# เว็บ 1-25   นาทีที่ 0,30
*/30 * * * *  cd /www/wwwroot/site01 && /www/server/php/83/bin/php wp-cron.php >/dev/null 2>&1

# เว็บ 26-50  นาทีที่ 5,35
5,35 * * * *  cd /www/wwwroot/site26 && /www/server/php/83/bin/php wp-cron.php >/dev/null 2>&1
```

## 5.6 Monitoring

### คำสั่งตรวจสถานะ

```bash
bash scripts/healthcheck.sh
```

### ⚠️ อย่าเชื่อตัวเลข % ใน aaPanel Dashboard

CyberPanel/aaPanel วัด CPU แบบ **snapshot ชั่วขณะ** ทำให้กระโดดไปมา (เคยเห็น 4% → 50% → 28%)
และมันนับ `%nice` (งาน background priority ต่ำ) รวมเข้าไปด้วย ทั้งที่งานพวกนั้นไม่ขวางทางเว็บเลย

| เครื่องมือ | เชื่อถือได้ |
|---|---|
| **`load average`** (`uptime`) | ✅ **ใช้ตัวนี้เป็นหลัก** |
| `mpstat 2 5` | ✅ |
| **Swap used** | ✅ ตัวเตือน RAM ไม่พอที่ดีที่สุด |
| aaPanel Dashboard % | ❌ |

### เกณฑ์สำหรับเครื่อง 4 cores

| Load average (5 นาที) | สถานะ |
|---|---|
| < 1.0 | ว่าง |
| 1.0 – 2.0 | ปกติ |
| 2.0 – 4.0 | เริ่มหนัก ควรดูสาเหตุ |
| > 4.0 | เกินกำลัง |

### แนะนำติดตั้งเพิ่ม

- **Uptime Kuma** (self-host ฟรี) หรือ UptimeRobot — แจ้งเตือนเข้า LINE/Discord เมื่อเว็บล่ม
- **Netdata** — กราฟย้อนหลังละเอียดวินาทีต่อวินาที (กิน RAM ~100–200 MB)
