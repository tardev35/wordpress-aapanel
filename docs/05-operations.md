## 5.1 ตารางงานประจำ

## 5.1b งานที่ทำอัตโนมัติทุกคืน 🤖

**ติดตั้งครั้งเดียว แล้วไม่ต้องมานั่งรันเองทุกวัน**

### 🕐 กับดักเรื่องเวลา — อ่านก่อนตั้ง ไม่ว่าจะตั้งวิธีไหน

**เครื่องนี้ตั้ง timezone เป็น UTC** (`timedatectl` → `Etc/UTC`) ดังนั้น:

```
23:00 เวลาไทย  =  16:00 บนเครื่อง
```

**หน้า Cron ของ aaPanel ก็ใช้เวลาเครื่อง ไม่ใช่เวลาไทย** — หลักฐานจากงานที่มีอยู่แล้วบนเครื่องนี้:
หน้าเว็บแสดงว่ารันตอน `8:46` และในไฟล์ `crontab` คือ `46 8 * * *` ตรงกันเป๊ะ

**ใส่ `23:00` ตรง ๆ ไม่ว่าที่ไหน = ไปรัน 6 โมงเช้าของวันถัดไปตามเวลาไทย**

### ทาง A: หน้า Cron ของ aaPanel ⭐ แนะนำ

ทีม**มองเห็นและกดดูเองได้** ทั้งสถานะ เวลารันล่าสุด และ log — ต่างจากบรรทัดใน `crontab`
ที่ไม่โผล่ในหน้า panel เลย

คัดลอกไฟล์ขึ้นเครื่องก่อน โดยสั่งไม่ให้มันไปแตะ crontab:

```powershell
scp -r configs scripts root@SERVER_IP:/tmp/wpaa/
ssh root@SERVER_IP "bash /tmp/wpaa/scripts/install-autoheal.sh --no-cron"
```

แล้วไป **aaPanel → Cron Job → Add Task**:

| ช่อง | ค่า |
|---|---|
| Task type | **Shell Script** |
| Task name | `wpaa nightly check` |
| Execute cycle | **Daily** · `16` : `00` ← **16 ไม่ใช่ 23** |
| Execute user | **root** |
| Script content | `/root/wpaa/scripts/nightly-check.sh` |

ช่อง Script content ใส่แค่บรรทัดเดียวเรียกสคริปต์ — **อย่าก๊อปเนื้อสคริปต์มาวาง**
ไม่งั้นจะมีโค้ดสองชุดให้ต้องไล่แก้ตามกันทุกครั้งที่อัปเดต repo

### ทาง B: crontab ตรง ๆ

```powershell
ssh root@SERVER_IP "bash /tmp/wpaa/scripts/install-autoheal.sh"
```

ใส่เป็น `0 16 * * *` พร้อม `flock` กันรันซ้อน · ถอดออกด้วย:

```powershell
ssh root@SERVER_IP "bash /tmp/wpaa/scripts/install-autoheal.sh --remove-cron"
```

> ⚠️ **เลือกทางเดียว** ถ้าเคยตั้งทาง B แล้วจะย้ายไปทาง A ต้องถอดของเดิมออกก่อน
> ไม่งั้นรันวันละ 2 รอบ — เช็คด้วย `crontab -l | grep wpaa`
>
> ตั้งใจไม่ใช้ `CRON_TZ=Asia/Bangkok` (ซึ่งจะทำให้เขียน 23:00 ได้ตรง ๆ) เพราะ `CRON_TZ`
> มีผลกับ **ทุกบรรทัดที่อยู่ถัดจากมัน** ในไฟล์เดียวกัน จะไปเลื่อนเวลางาน cron ของ aaPanel
> ที่อยู่ในไฟล์นั้นด้วยโดยไม่มีใครรู้

### สิ่งที่มันทำทุกคืน

| ตรวจ | ถ้าเจอปัญหา |
|---|---|
| `enable-php-83-wpfastcgi.conf` ถูก WP Toolkit เขียนทับ | กู้ฉบับที่จูนแล้วกลับ + ล้าง cache |
| `0.catchall_ssl.conf` หาย | ติดตั้งกลับ |
| ไซต์ที่ยังไม่ได้ stamp (ไม่มี `00-common.conf`) | ใส่กฎกลางให้ |

**มันแก้ให้เลย ไม่ใช่แค่รายงาน** เพราะวิธีแก้คือเอาไฟล์ที่รู้ว่าถูกไปทับ ซึ่งไม่ต้องใช้วิจารณญาณ
แต่จะแตะเฉพาะตอนที่ต่างจริง และ **`nginx -t` ก่อน reload เสมอ** ถ้าไม่ผ่านจะไม่ reload
ของเดิมยังวิ่งอยู่และเขียนลง log ไว้ให้เข้าไปดู

### 🔴 มันคือตาข่ายนิรภัย ไม่ใช่ตัวแทนของ `stamp-site.sh`

ถ้าเพิ่มเว็บตอน 10 โมงแล้วรอให้ cron 5 ทุ่มมาเก็บกวาด **โดเมนนั้นจะเสิร์ฟเว็บของลูกค้าคนอื่น
อยู่ 13 ชั่วโมง** และ FastCGI cache จะเก็บหน้าผิดนั้นไว้ตลอดช่วงเวลานั้นด้วย
(ดู [04 §4.5](04-cache.md)) — **ยังต้องรัน `stamp-site.sh` ทันทีหลัง Add site เหมือนเดิม**
cron มีไว้จับกรณีที่คนลืม ไม่ได้มีไว้ให้ตั้งใจลืม

### ✅ ทดสอบว่ามันซ่อมได้จริงแล้ว (2026-08-23)

รันเฉย ๆ แล้วได้ `[ok] ไม่มีอะไรเปลี่ยน` **ยังไม่นับว่าทดสอบ** — มันพิสูจน์แค่ทางที่ไม่มีอะไรผิด
หลักเดียวกับ backup ที่ไม่เคย restore ก็ยังไม่นับว่าเป็น backup

จึงทำให้พังจริงแล้วดูว่ามันกู้กลับ:

| ทำให้พัง | ผล |
|---|---|
| ลบ symlink `00-common.conf` ของไซต์หนึ่งทิ้ง | ตรวจเจอ → สร้างกลับ → `nginx -t` → reload |
| เติมบรรทัดเข้าไปใน `enable-php-83-wpfastcgi.conf` ให้ต่างจากต้นฉบับ | ตรวจเจอ → สำรองฉบับที่เพี้ยนไว้ → กู้ต้นฉบับกลับ → reload → **ล้าง cache 59 ไฟล์เหลือ 0** |

หลังทดสอบ: ทุกโดเมนยังเสิร์ฟเว็บตัวเอง · โดเมนแปลกหน้ายังได้ 404 · `X-Cache: HIT` กลับมาทันที

**ทดสอบซ้ำเองได้ทุกเมื่อ** (ปลอดภัย เพราะสคริปต์สำรองก่อนทับเสมอ):

```bash
# จำลองว่า WP Toolkit มาเขียนทับ
echo "# test" >> /www/server/nginx/conf/enable-php-83-wpfastcgi.conf
/root/wpaa/scripts/nightly-check.sh
tail -5 /var/log/wpaa-nightly.log
```

### ดู log

```bash
tail -30 /var/log/wpaa-nightly.log
crontab -l | grep wpaa          # ยืนยันว่าตั้งไว้จริง
```

> ถ้าตั้งด้วย **ทาง A** จะเห็นผลรันในหน้า Cron ของ panel ได้เลย
> ถ้าตั้งด้วย **ทาง B** บรรทัดนั้นจะไม่โผล่ในหน้า panel เพราะ panel อ่านจากฐานข้อมูลของตัวเอง
> ไม่ได้อ่าน `crontab` ตรง ๆ — ต้องดูด้วย `crontab -l` เท่านั้น
> เป็นเหตุผลหลักที่แนะนำทาง A

## 5.2 ⚠️ หลังอัปเดต aaPanel ทุกครั้ง

**การอัปเดตอาจเขียนทับไฟล์ที่เราแก้เอง** (สังเกตว่าไฟล์ `enable-php-*` ตัวอื่นลงวันที่จากตัวติดตั้ง)

### สคริปต์ตรวจ

```bash
ssh root@SERVER_IP "bash -s" < scripts/verify-config.sh
```

> 📌 **รอบ 2026-08-23 สคริปต์นี้จับ drift ได้จริง** — รายงานว่าเครื่องอ้างอิง ไม่มี `fastcgi_cache_lock`,
> ไม่มี `use_stale`, ยังมี `Cache-Control: max-age=0` และ Redis ไม่มี `maxmemory`
> ทั้งที่เอกสารรุ่นแรกเขียนเหมือนทำครบแล้วทุกข้อ
>
> บทเรียน: **"เขียนไว้ในเอกสาร" กับ "ทำแล้วบนเครื่อง" เป็นคนละเรื่อง** และต่างกันได้ตั้งแต่วันแรก
> ไม่ใช่แค่ตอนอัปเดต panel เขียนทับ — ให้รันสคริปต์นี้ตอนรับเครื่องใหม่มาดูแลด้วย ไม่ใช่เฉพาะหลังอัปเดต

หรือตรวจด้วยมือ:

```bash
# FastCGI cache config
grep -c "fastcgi_cache_lock" /www/server/nginx/conf/enable-php-83-wpfastcgi.conf
# ได้ 0 = โดนเขียนทับ → กู้จาก .bak-*

# PHP-FPM
grep -E "^pm |^pm\.max_children" /www/server/php/83/etc/php-fpm.conf
# ต้องได้ ondemand / 35

# MySQL
mysql -uroot -p -e "SHOW VARIABLES LIKE 'innodb_buffer_pool_size';"
# ต้องได้ 4294967296
```

### ไฟล์ที่ต้องเฝ้าระวัง

| ไฟล์ | ความเสี่ยง |
|---|---|
| `/www/server/nginx/conf/enable-php-83-wpfastcgi.conf` | **สูง** — WP Toolkit เขียนทับได้ |
| `/www/server/php/83/etc/php-fpm.conf` | ปานกลาง |
| `/www/server/php/83/etc/php.ini` | ปานกลาง |
| `/etc/my.cnf` | ต่ำ |
| `/etc/sysctl.d/99-tuning.conf` | ต่ำ (ไม่ใช่ของ aaPanel) |

## 5.3 Backup 🔴

> **สถานะปัจจุบัน: ยังไม่ได้ตั้ง — นี่คืองานที่เร่งด่วนที่สุด**
> เว็บ production ที่ไม่มี backup = ถ้าพัง ข้อมูลหายถาวร

### หลักการ 3-2-1

- **3** สำเนา
- **2** สื่อที่ต่างกัน
- **1** อยู่นอกสถานที่ (offsite)

### ชั้นที่ 1 — Hostinger VPS Backup (มีอยู่แล้ว)

- อัตโนมัติ **รายสัปดาห์** ฟรี เก็บสูงสุด 4 ชุด
- เก็บแยกจากเซิร์ฟเวอร์ ไม่หักโควตาดิสก์
- **ไม่สามารถเปลี่ยนเวลาได้**

### ⚠️ ข้อจำกัดของ Snapshot

- **เก็บได้ครั้งละ 1 ชุดเท่านั้น** — สร้างใหม่จะเขียนทับของเดิม
- **หมดอายุใน 1 วัน**
- **ถูกลบถ้าติดตั้ง OS ใหม่หรือ restore จาก backup**

**แปลว่า snapshot ใช้เป็นตาข่ายชั่วคราวระหว่างทำงานวันนั้นเท่านั้น ไม่ใช่ backup จริง**

### ชั้นที่ 2 — aaPanel → Offsite (ต้องตั้ง)

**aaPanel → Cron → Add task**

| ช่อง | ค่า |
|---|---|
| Type | Backup site / Backup database |
| Schedule | ทุกวัน 03:00 |
| Backup to | **S3-compatible** (Backblaze B2 / Cloudflare R2) |
| Keep | 7 ชุด |

**ค่าใช้จ่าย:** ~200 GB ≈ **฿600/ปี**
เทียบกับ Hostinger daily backup add-on ฿419/เดือน = ฿5,028/ปี → **ต่างกัน 8 เท่า**

### 🔴 ข้อที่ห้ามข้าม

> **หลังตั้ง backup เสร็จ ต้อง restore จริง 1 เว็บทันที**
> **backup ที่ไม่เคยกู้คืนสำเร็จ ยังไม่นับว่าเป็น backup**

## 5.4 SMTP ภายนอก 🔴

**อย่าให้ WordPress ส่งอีเมลจาก VPS โดยตรง** — IP ใหม่ไม่มีชื่อเสียง เมลจะเข้า spam
หรือถูกปฏิเสธ (ผู้ให้บริการอีเมลปฏิเสธเมลจาก IP ที่ forward/reverse DNS ไม่ตรงกัน)

### ติดตั้งทุกเว็บ

ปลั๊กอิน **WP Mail SMTP** → ชี้ไปบริการภายนอก

| บริการ | ฟรี | เหมาะกับ |
|---|---|---|
| Brevo | 300 เมล/วัน | ทีมเล็ก, ฟอร์มติดต่อ |
| Amazon SES | ~$0.10/1,000 | ปริมาณเยอะ ถูกที่สุด |
| Resend | 3,000/เดือน | ตั้งค่าง่ายที่สุด |

**ตั้ง SPF, DKIM, DMARC ใน DNS ของ Cloudflare ด้วย**

## 5.5 wp-cron

**ปิด wp-cron ในตัว** — ถ้าปล่อยไว้ 100 เว็บจะทริกเกอร์ cron ทุกครั้งที่มีคนเข้า

`wp-config.php`:
```php
define('DISABLE_WP_CRON', true);
define('WP_POST_REVISIONS', 5);
define('EMPTY_TRASH_DAYS', 14);
define('AUTOSAVE_INTERVAL', 120);
```

**ตั้ง system cron แทน — กระจายเวลาไม่ให้ยิงพร้อมกัน:**

```
# เว็บ 1-25   นาทีที่ 0,30
*/30 * * * *  cd /www/wwwroot/site01 && /www/server/php/83/bin/php wp-cron.php >/dev/null 2>&1

# เว็บ 26-50  นาทีที่ 5,35
5,35 * * * *  cd /www/wwwroot/site26 && /www/server/php/83/bin/php wp-cron.php >/dev/null 2>&1
```

## 5.6 Monitoring

### คำสั่งตรวจสถานะ

```bash
bash scripts/healthcheck.sh
```

### ⚠️ อย่าเชื่อตัวเลข % ใน aaPanel Dashboard

CyberPanel/aaPanel วัด CPU แบบ **snapshot ชั่วขณะ** ทำให้กระโดดไปมา (เคยเห็น 4% → 50% → 28%)
และมันนับ `%nice` (งาน background priority ต่ำ) รวมเข้าไปด้วย ทั้งที่งานพวกนั้นไม่ขวางทางเว็บเลย

| เครื่องมือ | เชื่อถือได้ |
|---|---|
| **`load average`** (`uptime`) | ✅ **ใช้ตัวนี้เป็นหลัก** |
| `mpstat 2 5` | ✅ |
| **Swap used** | ✅ ตัวเตือน RAM ไม่พอที่ดีที่สุด |
| aaPanel Dashboard % | ❌ |

### เกณฑ์สำหรับเครื่อง 4 cores

| Load average (5 นาที) | สถานะ |
|---|---|
| < 1.0 | ว่าง |
| 1.0 – 2.0 | ปกติ |
| 2.0 – 4.0 | เริ่มหนัก ควรดูสาเหตุ |
| > 4.0 | เกินกำลัง |

### แนะนำติดตั้งเพิ่ม

- **Uptime Kuma** (self-host ฟรี) หรือ UptimeRobot — แจ้งเตือนเข้า LINE/Discord เมื่อเว็บล่ม
- **Netdata** — กราฟย้อนหลังละเอียดวินาทีต่อวินาที (กิน RAM ~100–200 MB)
