## 10.1 เลือกเครื่องยังไง

### ตัวเลขฐานไว้เทียบ — เครื่องที่ใช้อยู่กินเท่าไหร่

ก่อนเลือกสเปกใหม่ ควรรู้ก่อนว่าของเดิมใช้จริงเท่าไหร่ วัดจาก `187.52.122.249`
เมื่อ 2026-08-25 ตอนมี **78 ไซต์**:

```
RAM  : ใช้จริง 2.0 Gi จาก 15 Gi   (อีก 11 Gi เป็น buff/cache = ว่าง)
Load : 0.91 จาก 4 cores
Disk : 28 GB จาก 194 GB
```

**อ่านตัวเลขนี้ยังไง** — 78 ไซต์กินราว 1 ใน 4 ของ KVM 4 คิดคร่าว ๆ คือ
**~2.5 MB RAM ต่อไซต์ที่อยู่เฉย ๆ** และ **~0.36 GB disk ต่อไซต์** เอาไปคูณจำนวนไซต์
ที่ตั้งใจจะใส่ในเครื่องใหม่ได้เลย

> ตัวเลขนี้เป็นสภาพ "แคชติดแล้ว ทราฟฟิกปกติ" ไม่ใช่ตอนพีค · ค่าที่ควรเผื่อจริง ๆ คือ
> ตอนทีมเพิ่มเว็บทีละหลายสิบตัวตอนเช้า ซึ่ง PHP-FPM กับ MariaDB ทำงานพร้อมกันหนัก
> ที่สุดในรอบวัน

### ⚠️ ถ้าย้ายไปเครื่องใหม่ อย่ายกค่าจูนเดิมไปทั้งชุด

ตอนตรวจเครื่องปัจจุบันพบว่า **MariaDB ไม่เคยถูกจูนตาม [03 §3.4](03-tuning.md) เลย**
ทั้ง 2 เครื่อง (`innodb_buffer_pool_size` เป็น `1024M` ทั้งที่ควรเป็น `4096M`,
`max_connections` เป็น `400` ทั้งที่ควรเป็น `200`)

เครื่องใหม่มีข้อได้เปรียบตรงที่ยังไม่มีเว็บ production — **ตั้งให้ถูกตั้งแต่แรกใช้เวลา
ไม่กี่นาที ส่วนการตามแก้ตอนมี 78 เว็บต้องนัดเวลา restart MariaDB**
ใช้ตาราง [หัวข้อ 10.8](#108-ค่าจูนเมื่อเครื่องไม่ใช่-4-vcpu--16-gb) เทียบทีละค่า

### ถ้าจะซื้อจริง — ดูอะไรบ้าง

| สิ่งที่ต้องดู | ทำไม |
|---|---|
| **RAM** | ตัวจำกัดตัวจริงของงานนี้ MariaDB buffer pool + PHP workers + Redis + FastCGI cache แย่งกันอยู่ในนี้ |
| **จำนวน vCPU** | สำคัญรองลงมา — WordPress ที่แคชแล้วแทบไม่แตะ CPU |
| **NVMe ไม่ใช่ SSD ธรรมดา** | 78 ไซต์ = 78 ฐานข้อมูล การอ่านสุ่มเยอะ |
| **Region** | latency จากไทย: Singapore ~30–40 ms · EU ~250–270 ms |
| **ราคาต่ออายุ** | ราคาโปรเป็นปีแรก ดู [01 §1.1](01-provisioning.md) |

### เทียบตัวเลือกที่เคยดูไว้

| เครื่อง | vCPU | RAM | Disk | หมายเหตุ |
|---|---|---|---|---|
| Hostinger **KVM 4** (ที่ใช้อยู่) | 4 | 16 GB | 200 GB | รับ 78 ไซต์ที่ load 0.9 |
| Hostinger **Cloud VPS 8** | 8 | 24 GB | 300 GB | ~2 เท่าของที่ใช้อยู่ |
| **Contabo** | ถูกกว่าที่สเปกเท่ากัน | | | ⚠️ ดูด้านล่าง |

> ⚠️ **Contabo ถูกกว่าจริง แต่ต้องรู้ก่อน 3 ข้อ**
> ราคาที่โฆษณามักเป็น region ยุโรป — **Singapore คิดเพิ่ม** ต้องกดเลือกแล้วดูราคาจริง ·
> ไม่มี OS template ของ aaPanel ต้องใช้หน้านี้ลงเอง · อ่านรีวิวเรื่อง disk I/O ก่อน
> เพราะงานนี้ไวกับ disk มากกว่า CPU
>
> **ยังไม่เคยทดสอบ Contabo จริงในโปรเจกต์นี้** ถ้าย้ายไปให้จดผลจริงลงหน้านี้แทนบรรทัดนี้

**Region ที่เลือก: Singapore** — ต่อให้ EU ฟรีก็ไม่คุ้ม 270 ms

## 10.3 🔴 timezone ต้องเป็น UTC — ห้ามเปลี่ยนเป็นเวลาไทย

```bash
timedatectl set-timezone UTC
timedatectl        # ต้องได้ Time zone: UTC (UTC, +0000)
```

**นี่ไม่ใช่เรื่องความชอบส่วนตัว** — คู่มือชุดนี้คำนวณเวลา cron จาก UTC ทั้งหมด
งานประจำคืนตั้งไว้ `0 16 * * *` ซึ่ง **แปลว่า 23:00 เวลาไทยก็ต่อเมื่อเครื่องเป็น UTC**

ถ้าใครมาตั้งเป็น `Asia/Bangkok` ทีหลัง งานนั้นจะไปรันตอน 16:00 ของไทยแทน
โดยไม่มีอะไรฟ้อง และ [05 §5.1b](05-operations.md) อธิบายไว้ว่าทำไมถึงไม่ใช้ `CRON_TZ` แก้

ตั้งชื่อเครื่องให้รู้ว่าเป็นตัวไหนด้วย:

```bash
hostnamectl set-hostname wpaa-sg-02      # ชื่อที่สื่อ ไม่ใช่ srv1234567
```

## 10.4 Swap + sysctl — ทำก่อนลง panel

ทำตอนนี้เพราะเป็นค่าระดับ OS ที่ panel ไม่ยุ่งด้วย และเป็นตาข่ายที่ควรมีตั้งแต่ก่อนมีอะไรให้พัง

### Swap

```bash
free -h                       # เช็คก่อน บาง image ให้มาแล้ว
```

ถ้า `Swap: 0B`:

```bash
fallocate -l 4G /swapfile
chmod 600 /swapfile
mkswap /swapfile
swapon /swapfile
echo '/swapfile none swap sw 0 0' >> /etc/fstab
```

**4 GB พอสำหรับทุกขนาดเครื่องในตารางข้างบน** swap คือตาข่ายกัน OOM killer ฆ่า MariaDB
ทิ้ง ไม่ใช่ที่ทำงานประจำ — ถ้าเครื่องแตะ swap บ่อยแปลว่า RAM ไม่พอจริง ต้องแก้ที่ค่าจูน
ไม่ใช่เพิ่ม swap (ดู [02 §2.2](02-hardening.md))

### sysctl + BBR

ไฟล์พร้อมใช้อยู่ใน repo แล้ว:

```powershell
scp configs/99-tuning.conf root@NEW_IP:/etc/sysctl.d/
ssh root@NEW_IP "echo tcp_bbr > /etc/modules-load.d/bbr.conf && modprobe tcp_bbr && sysctl --system"
ssh root@NEW_IP "sysctl net.ipv4.tcp_congestion_control"    # ต้องได้ bbr
```

รายละเอียดว่าแต่ละบรรทัดทำอะไรอยู่ใน [03 §3.1](03-tuning.md)

## 10.5 SSH key — ทำก่อนเปิดพอร์ตอะไรทั้งนั้น

บอทสแกนเจอ IP ใหม่ภายในไม่กี่ชั่วโมง และพอร์ต 22 เปิดอยู่แล้วตั้งแต่วินาทีแรก

**บนเครื่องตัวเอง** (ถ้ายังไม่มีคีย์):

```powershell
ssh-keygen -t ed25519 -C "wpaa"
type $env:USERPROFILE\.ssh\id_ed25519.pub | ssh root@NEW_IP "mkdir -p ~/.ssh && chmod 700 ~/.ssh && cat >> ~/.ssh/authorized_keys && chmod 600 ~/.ssh/authorized_keys"
```

**ทดสอบว่าคีย์ใช้ได้ก่อน** แล้วค่อยปิด password:

```powershell
ssh root@NEW_IP "echo คีย์ใช้ได้"
```

> 🔴 **ห้ามปิด password login ก่อนทดสอบคีย์สำเร็จ** ถ้าคีย์พังแล้วปิด password ไปแล้ว
> จะเหลือทางเดียวคือ console ของผู้ให้บริการ · ขั้นตอนเต็มอยู่ใน [02 §2.3](02-hardening.md)

## 10.6 ติดตั้ง aaPanel

คำสั่งทางการสำหรับ Ubuntu/Debian (ตรวจจาก aapanel.com เมื่อ 2026-08-25):

```bash
URL=https://www.aapanel.com/script/install_panel_en.sh && \
if [ -f /usr/bin/curl ]; then curl -ksSO $URL; else wget --no-check-certificate -O install_panel_en.sh $URL; fi; \
bash install_panel_en.sh
```

ตอบ `y` เมื่อถามยืนยัน · ใช้เวลาราว 5–10 นาที

> ⚠️ **สังเกต `-k` และ `--no-check-certificate`** — ตัวติดตั้งของ aaPanel สั่งข้าม
> การตรวจใบรับรอง TLS เอง แปลว่าถ้ามีใครดักกลางทางได้ ก็ยัดสคริปต์อะไรมาก็ได้
> ถ้าจะให้แน่นกว่านั้น โหลดแยกแล้วอ่านก่อนรัน:
>
> ```bash
> curl -sSO https://www.aapanel.com/script/install_panel_en.sh   # ไม่ใส่ -k
> less install_panel_en.sh
> bash install_panel_en.sh
> ```

**พอเสร็จมันจะพ่น URL / username / password ออกมาครั้งเดียว — คัดลอกเก็บทันที**
ถ้าพลาดก็เรียกใหม่ได้:

```bash
bt default
```

## 10.9 เรื่องแคชที่จะเจอแน่ ถ้าไม่ตั้งให้ครบ

อาการที่ทีมจะมาบอกคือ **"แก้เนื้อหาแล้วหน้าเว็บไม่เปลี่ยน"** ซึ่งบนเครื่องที่ตั้งไม่ครบ
มีต้นเหตุได้ 5 อย่าง และ**ทุกอย่างเงียบเหมือนกันหมด — กดปุ่มได้ ไม่มี error ไม่มีอะไรเกิดขึ้น**

ตารางเต็มพร้อมวิธีพิสูจน์อยู่ที่ [04 §4.7](04-cache.md) · สรุปสั้น ๆ:

| # | ต้องเป็น | ถ้าผิดจะเป็นยังไง |
|---|---|---|
| 1 | `RT_WP_NGINX_HELPER_CACHE_PATH` ชี้โฟลเดอร์ที่ nginx ใช้จริง | ปลั๊กอินลบไฟล์ในโฟลเดอร์ว่าง สำเร็จทุกครั้ง ไม่มีผล |
| 2 | `open_basedir` เปิดให้ PHP แตะโฟลเดอร์นั้น | `open_basedir restriction in effect` |
| 3 | มีไฟล์ปลั๊กอิน `nginx-helper` | ไม่มีอะไรมาล้างให้ |
| 4 | ปลั๊กอิน activate | เหมือนข้อ 3 |
| 5 | `purge_method = unlink_files` | ยิง `/purge/` ออกไปแล้วโดน `deny` (เห็นใน error log) |

`fix-cache-purge.sh` ตั้งให้ครบทั้ง 5 ข้อ และ `watch-new-sites.sh` ตามซ่อมให้ไซต์ใหม่เอง

### ⚠️ ห้ามลงปลั๊กอินแคชตัวอื่นซ้อน

บนเครื่องที่ใช้อยู่มี **56 ไซต์ที่มีปลั๊กอินแคชซ้อนอยู่** (`wp-rocket` 28 · `litespeed-cache` 27
· `wp-fastest-cache` 1) เวลาเนื้อหาไม่อัปเดตจะแยกไม่ออกว่าใครเก็บไว้

**`litespeed-cache` แทบไม่ทำอะไรเลยบนเครื่องที่ใช้ nginx** เพราะมันต้องการ LiteSpeed server
— เจอไซต์ที่เปิด `litespeed-cache` แล้วปิด `nginx-helper` ไว้ คือได้ปลั๊กอินที่ไม่ทำงาน
แล้วปิดตัวที่ทำงาน

**เครื่องใหม่ให้เหลือ FastCGI cache + Nginx Helper ชั้นเดียว** ถ้าอยากได้ minify/lazyload
ให้เปิดเฉพาะฟีเจอร์นั้นในปลั๊กอิน อย่าเปิด page cache ของมัน

### ⚠️ Cloudflare คือแคชอีกชั้นที่ผมสั่งไม่ได้

ถ้าล้างที่เครื่องแล้วยังเห็นของเก่า ให้ดู response header ในเบราว์เซอร์:

| เห็น | ค้างที่ | ล้างที่ |
|---|---|---|
| `cf-cache-status: HIT` | Cloudflare | Cloudflare → Caching → Purge Everything |
| `x-cache: HIT` แต่เนื้อหาเก่า | เครื่องเรา | `clear-cache.sh DOMAIN` |

> 🔴 **เวลาทดสอบด้วย `curl` ต้องใส่ `-A "Mozilla/5.0"` เสมอ** — บาง zone เปิด Bot Fight Mode
> ไว้ ซึ่งตอบ `403` ให้ทุก client ที่ไม่ใช่เบราว์เซอร์ ถ้าไม่ใส่จะเข้าใจผิดว่าเว็บพัง
> (และ Bot Fight Mode ยังทำให้ **Let's Encrypt ขอ cert ไม่ผ่าน** ด้วย ดู [07 ข้อ 14](07-troubleshooting.md))

**สิ่งที่หน้านี้ทำไปแล้ว จะข้ามได้ในหน้าอื่น:** swap ([02 §2.2](02-hardening.md)) ·
sysctl + BBR ([03 §3.1](03-tuning.md)) · SSH key ([02 §2.3](02-hardening.md))

## 10.8 ค่าจูนเมื่อเครื่องไม่ใช่ 4 vCPU / 16 GB

ตัวเลขใน [03-tuning](03-tuning.md) ผูกกับเครื่อง **4 vCPU / 16 GB** ถ้าเครื่องใหม่ใหญ่กว่า
อย่าคูณทุกค่าขึ้นตามสัดส่วน — บางค่าโตตาม RAM บางค่าไม่เกี่ยวกับขนาดเครื่องเลย

| ค่า | 4 vCPU / 16 GB | 8 vCPU / 24 GB | โตตามอะไร |
|---|---|---|---|
| `pm.max_children` (PHP-FPM) | `35` | **`60`** | RAM ที่เหลือหลังหักตัวอื่น ÷ 80 MB แล้วตัดด้วยจำนวน core |
| `pm` | `ondemand` | **`ondemand`** | ไม่เปลี่ยน — ดู [03 §3.2](03-tuning.md) |
| `innodb_buffer_pool_size` | `4096M` | **`6144M`** | ~25% ของ RAM |
| `max_connections` | `200` | **`200`** | ไม่เปลี่ยน — ผูกกับ `max_children` ไม่ใช่ RAM |
| `join_buffer_size` | `256K` | **`256K`** | ไม่เปลี่ยน — จองแยกต่อ connection ยิ่งใหญ่ยิ่งเปลือง |
| Redis `maxmemory` | `1gb` | **`2gb`** | ตามจำนวนไซต์ |
| `opcache.memory_consumption` | `1024` | **`1024`** | ตามจำนวน **ไฟล์ PHP** ไม่ใช่ RAM |
| FastCGI `max_size` | `1g` | **`2g`** | ตามพื้นที่ disk |
| FastCGI `keys_zone` | `100m` | **`200m`** | ตามจำนวนหน้าที่แคช |
| `worker_processes` (nginx) | `auto` | **`auto`** | `auto` = ตามจำนวน core อยู่แล้ว |

### ⚠️ โปรไฟล์ใน GUI ของ MariaDB ยังต้องเลือก `4-8GB` เหมือนเดิม

[03 §3.4](03-tuning.md) บอกให้เลือก **Optimization plan = `4-8GB`** บนเครื่อง 16 GB
เพราะโปรไฟล์พวกนี้สมมติว่า MySQL ได้ RAM เกือบทั้งเครื่อง

**บนเครื่อง 24 GB ก็ยังเลือก `4-8GB` อยู่ดี** แล้วค่อยแก้ `innodb_buffer_pool_size`
เป็น `6144M` ด้วยมือ — ถ้าไปเลือก `8-16GB` มันจะตั้ง buffer pool ไว้ 8–10 GB
ซึ่งเกินงบที่กันไว้ในตารางข้างบน แล้วไปแย่ง RAM ของ PHP-FPM

### ที่มาของ `max_children = 60`

```
RAM 24 GB
 − 6 GB   MariaDB buffer pool
 − 2 GB   Redis
 − 3 GB   OS + nginx + OPcache + ส่วนอื่น
 = 13 GB  เหลือให้ PHP
13 GB ÷ 80 MB ต่อ worker ≈ 166 worker
```

**แต่ไม่ตั้ง 166** เพราะเพดานจริงคือ CPU ไม่ใช่ RAM — PHP 166 ตัวแย่งกัน 8 core
จะช้ากว่า 60 ตัวที่ได้ CPU เต็ม ๆ ตั้งราว 8 ตัวต่อ core แล้วปล่อย RAM ที่เหลือให้
page cache ของ Linux ใช้ ซึ่งมีประโยชน์กว่า worker ที่ได้แต่รอคิว

> 🔴 **ถ้าเปลี่ยนตัวเลขเพราะเครื่องใหญ่ขึ้น ต้องแก้เอกสารกับ `verify-config.sh`
> ให้ตรงกันด้วย** ไม่งั้นตัวตรวจจะฟ้องว่าค่าผิดทุกครั้งจนไม่มีใครอ่านมันอีก
> แล้ววันที่ค่าหลุดจริงก็จะไม่มีใครสังเกต
