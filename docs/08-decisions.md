# 08 — Decision Log

บันทึกการตัดสินใจสำคัญ เพื่อให้คนที่มาดูแลต่อเข้าใจว่าทำไมระบบเป็นแบบนี้

## ADR-001: เลือก Self-managed VPS แทน Managed Cloud Hosting

**วันที่:** สิงหาคม 2026

### บริบท

เดิมพิจารณา Hostinger **Cloud Professional** ราคาปีแรก ~฿5,300
แต่พบว่า **ราคาต่ออายุอยู่ที่ ~฿16,500/ปี** (ขึ้น ~3.1 เท่า)

### เปรียบเทียบ

| | Cloud Professional | **VPS KVM 4** |
|---|---|---|
| RAM | ~6 GB | **16 GB** |
| **เพดาน PHP processes** | **~60 concurrent** | **ไม่มี — ตั้งเอง** |
| Control panel | hPanel (บังคับ) | เลือกเองได้ |
| ใครแพตช์ OS | Hostinger | **เรา** |
| ย้ายไปเจ้าอื่น | ยาก | **ง่าย** |

### เหตุผลที่ตัดสินใจ

**เพดาน PHP processes คือปัจจัยชี้ขาด ไม่ใช่ราคา**

Cloud Professional จำกัด ~60 concurrent processes สำหรับทุกเว็บรวมกัน
พอถึงเพดาน เว็บที่เหลือจะเข้าคิวรอ — อาการที่ผู้ใช้เห็นคือเว็บโหลดช้าเป็นช่วง ๆ โดยหาสาเหตุไม่เจอ

และ 6 GB RAM เหมาะกับราว 40–60 เว็บทราฟฟิกต่ำเท่านั้น
**"สร้างได้ 100 เว็บ" กับ "รันไหว 100 เว็บ" เป็นคนละเรื่อง**

### ต้นทุนที่ยอมรับ

- เวลาดูแล ~2–3 ชม./เดือน
- ความรับผิดชอบด้าน security patch เป็นของเรา

### แผนระยะยาว

ปีที่ 1–2 อยู่กับ Hostinger (ease of use สูง)
**ปีที่ 3 ประเมินย้ายไป Contabo/Hetzner** ซึ่งไม่มีกับดักราคาต่ออายุ
→ ประหยัดได้ ~฿6,000/ปี และย้ายง่ายเพราะเราเป็นเจ้าของ stack เอง

## ADR-002: เปลี่ยนจาก CyberPanel เป็น aaPanel

**วันที่:** สิงหาคม 2026
**สถานะ:** ✅ ดำเนินการแล้ว (รื้อติดตั้งใหม่ตอนเครื่องยังว่าง)

### บริบท

เริ่มต้นด้วย CyberPanel + OpenLiteSpeed เพราะ LSCache
แต่พบปัญหาต่อเนื่องที่ทั้งหมด**เป็นข้อบกพร่องของตัว CyberPanel เอง**

### ปัญหาที่พบ

| ปัญหา | รายละเอียด |
|---|---|
| ค่า LSAPI ที่ตั้งไม่ถูกใช้จริง | CyberPanel สร้าง `extprocessor` แยกต่อเว็บ ไม่อ้างอิงค่าระดับ server |
| **ไม่มี `LSAPI_MAX_IDLE` ใน vhost** | process ไม่ปิดตัวเอง → **RAM ไม่ถูกคืน** |
| ค่าเริ่มต้น memory 1024M/เว็บ | 100 เว็บ × 1 GB = 100 GB (มี RAM แค่ 16 GB) |
| ต้องแก้ core code | `plogical/vhostConfs.py` ซึ่ง**โดนเขียนทับทุกครั้งที่อัปเดต** |
| **ติดตั้ง WordPress ไม่ได้เลย** | error `'WPVersion' [404]` — บั๊กในโค้ด |

**ประเด็นสุดท้ายคือตัวตัดสิน** — เน็ตเวิร์กของเซิร์ฟเวอร์ปกติสมบูรณ์
(ทดสอบ `curl https://wordpress.org` ได้ `HTTP/2 200`) แต่ตัว installer ล้มเหลว
สอดคล้องกับที่ WordPress ออกเวอร์ชันใหม่แล้วโค้ด CyberPanel ตามไม่ทัน

### เหตุผลที่ตัดสินใจ

ทีมจัดให้ **"ใช้งานง่าย" เป็นอันดับ 1** และระบุว่า **ทีมไม่คล่อง CLI**

CyberPanel ต้องการคนที่พร้อมซ่อมมันอยู่เรื่อย ๆ ซึ่งขัดกับข้อกำหนดนี้โดยตรง

### สิ่งที่ได้จาก aaPanel

| ข้อดี | รายละเอียด |
|---|---|
| **PHP-FPM pool เดียวร่วมกัน** | RAM ถูกจำกัดด้วย `pm.max_children` เท่านั้น — **ไม่ว่ามี 10 หรือ 100 เว็บ เพดาน RAM เท่ากัน** |
| **จุดแก้ config จุดเดียว** | `enable-php-83-wpfastcgi.conf` ใช้ร่วมทุกเว็บ |
| **WP Toolkit** | ติดตั้ง/cache/backup/clone ผ่าน GUI ทั้งหมด |
| RAM ต่ำกว่า | 301 MB ตอนว่าง vs CyberPanel 1.4 GB |

### สิ่งที่เสีย

- **ไม่ได้ LSCache** → ใช้ Nginx FastCGI Cache แทน (ผลใกล้เคียงกัน — วัดได้ 0.3 ms)
- **ทุกเว็บรัน user `www` เดียวกัน** → ดู [02-hardening §2.6](02-hardening.md)

### สิ่งที่ไม่เสียเปล่า

การจูน MariaDB, Redis, swap, sysctl ทั้งหมดอยู่ระดับ OS — ยังใช้ได้หลังเปลี่ยน panel

## ADR-003: Single WebServer model แทน Multi-WebServer

**เหตุผล:** WordPress ไม่ต้องการ `.htaccess` เมื่อใช้ Nginx
ส่วน Multi กิน RAM เพิ่ม ~30–40% และทำให้ **FastCGI Cache (หัวใจของแผน) ตั้งยากขึ้นมาก**

Multi เหมาะเฉพาะกรณีต้องย้ายเว็บเก่าที่มี rewrite rules ซับซ้อนใน `.htaccess` ซึ่งแก้ไม่ได้

## ADR-004: PHP 8.3 เป็นเวอร์ชันหลักเดียว

**เหตุผล:**
1. ปลั๊กอิน WordPress รองรับ 8.3 กว้างที่สุด (8.4 ยังมีบางตัวมีปัญหา)
2. อยู่ในช่วง active support ยาวกว่า
3. **ทุกเว็บใช้เวอร์ชันเดียวกัน = มีจุดแก้ config จุดเดียว**

8.0 / 8.1 หมดอายุการซัพพอร์ตแล้ว (ไม่ได้รับ security patch) → ถอนทิ้ง
8.4 เก็บไว้เป็นสำรอง `max_children = 5`

> **กฎ: ผลรวม `max_children` ของทุกเวอร์ชันต้องไม่เกิน 40**

## ADR-005: ไม่เปิด OPcache JIT

**เหตุผล:** WordPress เป็นงานที่รอฐานข้อมูลและดิสก์เป็นหลัก ไม่ใช่งานคำนวณ
JIT จึงแทบไม่ช่วย แถมเคยมีรายงานว่าทำให้ปลั๊กอินบางตัวมีปัญหา

**ตัวอย่างคลาสสิกของการจูนที่ฟังดูดีแต่ไม่ให้ผลจริง**

## ADR-006: `query_cache_size = 0`

**เหตุผล:** Query cache ใช้ **global lock** — ทุกครั้งที่เว็บใดเขียนข้อมูล จะล็อกทั้งระบบ

**เมื่อมี 100 ฐานข้อมูล การเขียนจากเว็บใดก็ตามจะทำให้อีก 99 เว็บรอ**

MySQL 8.0 ถอดฟีเจอร์นี้ออกแล้วด้วยเหตุผลเดียวกัน → ใช้ Redis object cache แทน

---

## ADR-007: ไม่ติดตั้ง FTP

**เหตุผล:** FTP ส่งรหัสผ่านแบบไม่เข้ารหัส และเป็นเป้าหมายยอดนิยมของบอทเดารหัสผ่าน

**ทางเลือกที่ปลอดภัยกว่า:** SFTP (ผ่าน SSH port 22) หรือ File Manager ใน aaPanel
ทีมที่ใช้ FileZilla อยู่แล้วก็ยังใช้ได้ แค่เปลี่ยนโปรโตคอลเป็น SFTP

## ADR-009: WordPress Multisite — ไม่ใช้

**เหตุผลที่ปฏิเสธ:**
- Database เดียวร่วมกัน → พังพร้อมกันทั้ง 100 เว็บ
- ปลั๊กอินหลายตัวไม่รองรับ multisite
- แยก backup/restore เว็บเดียวยากมาก
- ย้ายเว็บออกไปให้ลูกค้าทีหลังลำบาก

เหมาะเฉพาะกรณีทั้ง 100 เว็บเป็นขององค์กรเดียวและใช้ theme/plugin ชุดเดียวกัน

## ADR-010: กฎ nginx ของเราไปอยู่ใน `extension/<domain>/` ไม่แก้ vhost ตรง ๆ

**วันที่:** สิงหาคม 2026 · **สถานะ:** ✅ ใช้แล้วบนเครื่องอ้างอิง

### บริบท

เอกสารรุ่นแรกบอกให้แก้ config ผ่าน aaPanel GUI และ "ห้าม `sed -i`" ซึ่งแก้ปัญหาไฟล์พังได้
แต่ไม่ได้แก้ปัญหาอีกข้อ: **ไฟล์ vhost เป็นของ panel** มันเขียนทับได้ทุกครั้งที่ต่ออายุ SSL
เปลี่ยน setting ของไซต์ หรืออัปเดต panel — ไม่ว่าจะแก้ด้วยมือหรือด้วย GUI ก็หายเหมือนกัน

### สิ่งที่พบ

vhost ที่ aaPanel สร้างมีบรรทัดนี้อยู่แล้วตั้งแต่ต้น server block:

```nginx
include /www/server/panel/vhost/nginx/extension/<domain>/*.conf;
```

เป็นจุดที่ panel เปิดไว้ให้ใส่ของเราเอง และ **panel ไม่แตะไฟล์ในโฟลเดอร์นั้น**

### ตัดสินใจ

กฎ nginx ทุกอย่างที่เราเขียนเองไปอยู่ใน `extension/<domain>/` เท่านั้น:

| ไฟล์ | ใส่ให้ใคร |
|---|---|
| `00-common.conf` (symlink → `/www/server/nginx/conf/common-site.conf`) | ทุกไซต์ |
| `astro.conf` | เฉพาะเว็บ static |

**ทำเป็น symlink ไม่ใช่ copy** — แก้ต้นฉบับไฟล์เดียวมีผลทุกไซต์ทันที ตรงกับหลักการเดียวกับที่
`enable-php-83-wpfastcgi.conf` เป็นจุดกลางของเว็บ PHP ทุกตัว

### ผลข้างเคียงที่ดี

กฎกลางไม่มีชื่อโดเมนอยู่ข้างในเลย (ใช้ `$host` แทน) ไฟล์เดียวจึงใช้ได้กับทุกเว็บ
และย้ายไปเครื่องใหม่ได้โดยไม่ต้องแก้อะไร

## ADR-011: catch-all พอร์ต 443 — `return 404` + cert ของตัวเอง

**วันที่:** 2026-08-23 · **สถานะ:** ✅ ใช้แล้วบนเครื่องอ้างอิง

### บริบท

ดู [02-hardening §2.8](02-hardening.md) — ไม่มีใครประกาศ `default_server` บนพอร์ต 443
โดเมนแปลกหน้าจึงได้เว็บของลูกค้ารายที่ชื่อไฟล์เรียงมาก่อนสุด

### ทางเลือกที่พิจารณา

| ทาง | ทำไมไม่เลือก |
|---|---|
| `ssl_reject_handshake on` | สะอาดที่สุดในทางทฤษฎี (ไม่ต้องมี cert เลย) แต่ผู้ใช้จะเห็น error 525/526 ของ Cloudflare ซึ่งอ่านไม่ออกว่าเกิดอะไรขึ้น |
| ยืม cert ของไซต์ใดไซต์หนึ่ง | **อันตราย** — วันที่ไซต์นั้นถูกลบ nginx จะสตาร์ทไม่ขึ้นทั้งเครื่อง พาทุกเว็บล่มพร้อมกัน |
| ให้ catch-all กิน**พอร์ต 80 ด้วย** | หน้า "Website not found" ของ panel ที่อ่านรู้เรื่องจะหายไป และเสี่ยงกับ Let's Encrypt HTTP-01 ที่ต่ออายุผ่านพอร์ต 80 |

### ที่เลือก

```nginx
server {
    listen 443 ssl default_server;
    server_name _;
    ssl_certificate     /www/server/nginx/conf/catchall.crt;   # self-signed ของตัวเอง
    ssl_certificate_key /www/server/nginx/conf/catchall.key;
    if ($host ~* ^www\.(.+)$) { return 301 https://$1$request_uri; }
    return 404;
}
```

- **cert self-signed ของตัวเอง** ไม่ผูกกับไซต์ไหน ลบไซต์ไหนทิ้งก็ไม่กระทบ
- **404 ไม่ใช่ 444** — ผู้ใช้ได้หน้าที่บอกว่า "ไม่มีเว็บนี้" แทนที่จะเป็นการตัดสายเงียบ ๆ ที่ดูเหมือนเน็ตล่ม
- **`www.*` ได้ 301 ไป apex** ก่อนถึงบรรทัด 404 — กำไรที่ได้มาฟรี: ไซต์ที่ panel ไม่ได้ใส่ `www`
  ใน `server_name` ก็ได้ redirect ด้วยโดยไม่ต้องตั้งอะไรเพิ่ม
- **แตะเฉพาะพอร์ต 443** พอร์ต 80 ปล่อยให้ `0.default.conf` ของ panel ดูแลต่อ

### สิ่งที่ยังไม่ได้ทำ

ยังไม่ได้ใส่ `listen 443 quic default_server` — QUIC/h3 จะถูกใช้ก็ต่อเมื่อ client เคยได้ Alt-Svc
จาก response ที่สำเร็จมาก่อน ซึ่งแปลว่าโดเมนนั้นแมตช์ไซต์จริงอยู่แล้ว ความเสี่ยงจึงต่ำ
และการเพิ่ม listener ที่ยังไม่ได้ทดสอบมีโอกาสทำ `nginx -t` ล้มมากกว่าประโยชน์ที่ได้

## ADR-012: ปิด auto-update ของ WordPress ทั้งหมด

**วันที่:** 2026-08-23 · **สถานะ:** ✅ ใช้แล้วทุกไซต์ (19 ไซต์)

### บริบท

ตั้งแต่ **WordPress 5.6** การติดตั้งใหม่จะเปิด auto-update ระดับ **major** ให้เองโดยอัตโนมัติ
(ของเดิมอัปเฉพาะ minor/security) ผลคือเวอร์ชันที่เลือกใน WP Toolkit ไม่ใช่เวอร์ชันที่จะได้จริง

หลักฐานบนเครื่องนี้: `mooyim99-hub.com` เป็น `6.5.10` ตอน 14:00 และกลายเป็น `7.1`
ภายใน 14:23 โดยไม่มีใครสั่ง

> ⚠️ **แต่ไม่ใช่ทุกเคสที่เป็นเรื่อง auto-update** — ไซต์ที่สร้างหลังจากนั้นขึ้น 7.1 ตั้งแต่แรก
> เพราะ**ฟอร์ม Add WordPress เลือกเวอร์ชันล่าสุดเป็นค่าเริ่มต้น** ไม่เกี่ยวกับ ADR นี้เลย
> วิธีแยกสองเคสออกจากกันอยู่ที่ [06 §6.1](06-new-site.md) — ดูวันที่ของ `version.php`
> เทียบกับวันที่สร้างไซต์

### ทางเลือก

| ทาง | ข้อดี | ข้อเสีย |
|---|---|---|
| ปล่อยไว้ (major + minor) | ได้ security patch ทันที ไม่ต้องดูแล | major update พังธีม/ปลั๊กอินได้เงียบ ๆ พร้อมกัน 19 เว็บ |
| minor เท่านั้น | ได้ security patch · major ควบคุมเอง | ยังต้องไล่อัป major เองอยู่ดี |
| **ปิดทั้งหมด** ← ที่เลือก | ควบคุมได้เต็มที่ ไม่มีอะไรเปลี่ยนโดยไม่รู้ตัว | **ไม่ได้ security patch อัตโนมัติเลย** |

### เหตุผล

เจ้าของเลือกปิดทั้งหมด โดยรับข้อแลกเปลี่ยนเรื่อง security patch ไว้แล้ว

ปัจจัยที่หนักที่สุดคือ **เครื่องนี้ยังไม่มี backup สักชุด** — major update ที่พังเว็บลูกค้า
ในสภาพนี้แปลว่ากู้ไม่ได้ ความเสี่ยงจาก "อัปเดตแล้วพัง" จึงหนักกว่าความเสี่ยงจาก
"ช้าไปสองสามวันกว่าจะแพตช์" อยู่มากในตอนนี้

### ค่าที่ใช้

```php
define( 'AUTOMATIC_UPDATER_DISABLED', true );
```

เป็นสวิตช์ตัวเดียวที่ปิดทั้ง core, ปลั๊กอิน, ธีม และ translation
ใส่ด้วย [`scripts/set-wp-autoupdate.sh`](../scripts/set-wp-autoupdate.sh) ซึ่งสำรอง
`wp-config.php` ก่อนเสมอ ข้ามไซต์ที่ตั้งไว้แล้ว และ **ตรวจ `php -l` ก่อนเอาไปทับของจริง**
เพราะ `wp-config.php` พังคือเว็บดับสนิท (ทดสอบด้วยไฟล์ที่ syntax พังจริงแล้ว — มันข้ามให้)

### สิ่งที่ต้องทำแทน — ห้ามลืม

**งาน "อัปเดต WP ทุกสัปดาห์ผ่าน WP Toolkit" ใน [05 §5.1](05-operations.md) เปลี่ยนจาก
"ควรทำ" เป็น "ห้ามพลาด"** ตั้งแต่วันที่ ADR นี้มีผล เพราะไม่มีอะไรมาแพตช์ให้อีกแล้ว

และเมื่อไหร่ที่ backup พร้อมใช้จริง (restore สำเร็จแล้วอย่างน้อย 1 ครั้ง)
**ควรกลับมาทบทวน ADR นี้** — เหตุผลหลักที่เลือกปิดทั้งหมดคือไม่มีตาข่ายรองรับ
พอมีตาข่ายแล้ว `'minor'` อาจคุ้มกว่า

### ไซต์ใหม่จะรั่วเอง — จึงต้องมีตาข่าย

ไซต์ที่สร้างใหม่มาพร้อม auto-update เปิดเสมอ นโยบายนี้จึงรั่วทีละไซต์ทุกครั้งที่ทีมเพิ่มเว็บ
จึงปิดสามชั้น:

1. **[`watch-new-sites.sh`](../scripts/watch-new-sites.sh)** ที่ systemd เรียกให้เอง —
   เพิ่มทีหลังใน [ADR-013](#adr-013-ตาข่ายรอบกลางคืนช้าเกินไป--ให้เครื่องทำเอง)
2. **[`stamp-site.sh`](../scripts/stamp-site.sh)** ยังเรียกเองได้ทุกเมื่อ และเป็นตัวงานที่ข้อ 1
   เรียกใช้ — แต่ไม่ใช่ขั้นตอนที่คนต้องทำประจำอีกแล้ว
3. **[`nightly-check.sh`](../scripts/nightly-check.sh)** เรียก `set-wp-autoupdate.sh`
   ทุกคืนเป็นตาข่ายชั้นสุดท้าย เผื่อ unit ในข้อ 1 ถูกปิด

ทั้งสามเรียกสคริปต์ตัวเดียวกัน ไม่ได้เขียนตรรกะซ้ำ และมัน idempotent จึงรันซ้อนกันได้

## ADR-013: ตาข่ายรอบกลางคืนช้าเกินไป — ให้เครื่องทำเอง

**วันที่:** 2026-08-25 · **สถานะ:** ✅ ติดตั้งแล้วบน `187.52.125.203` (ทดสอบด้วยการทำให้พังจริง)

### บริบท — ตาข่ายที่ตาห่างกว่าเหยื่อ

[ADR-012](#adr-012-ปิด-auto-update-ของ-wordpress-ทั้งหมด) วางตาข่ายไว้สองชั้น แล้วชั้นบน
(คนรัน `stamp-site.sh` เอง) ก็หลุดจริงในครั้งแรกที่ใช้งาน:

| เวลาไทย | เกิดอะไรกับ `login-edo89.com` |
|---|---|
| 00:04 | panel ลง WordPress `6.7.7` — **ตรงตามที่เลือก คู่มือส่วนนั้นไม่ผิด** |
| 00:07 | เขียน `wp-config.php` โดยไม่มี `AUTOMATIC_UPDATER_DISABLED` (ไม่ได้รัน `stamp-site.sh`) |
| **01:08** | WordPress อัปตัวเองเป็น `7.1` — ห่างจากติดตั้ง **1 ชั่วโมง** |
| 23:00 | `nightly-check.sh` ถึงคิว — **สายไป 22 ชั่วโมง** |

ตาข่ายรอบกลางคืนถูกออกแบบมาจับ config drift ที่เกิดวันละครั้ง แต่ถูกเอามาใช้จับสิ่งที่
เกิดภายในชั่วโมงเดียว จึงไม่เคยจับได้เลย

### ข้อจำกัดที่กำหนดรูปของคำตอบ

**ทีมงานที่กด Add site ไม่ได้ใช้ cmd/ssh** ทางแก้ที่จบด้วยประโยค "แล้วให้รันคำสั่งนี้ด้วย"
จึงไม่ใช่ทางแก้ — มันแค่ย้ายความรับผิดชอบไปวางบนคนที่ทำไม่ได้ แล้วรอให้หลุดอีกรอบ

### ตัดสินใจ

เพิ่ม [`watch-new-sites.sh`](../scripts/watch-new-sites.sh) แล้วให้ **systemd เรียกเอง 2 ทาง**
ติดตั้งด้วย [`install-site-watcher.sh`](../scripts/install-site-watcher.sh)

| unit | ตื่นเมื่อ | ปิดช่องว่างอะไร |
|---|---|---|
| `wpaa-newsite.path` | `PathChanged=/www/server/panel/vhost/nginx` = วินาทีที่ panel เขียน vhost | nginx reload — วัดได้ **37 มิลลิวินาที** |
| `wpaa-newsite.timer` | ทุก 1 นาที | ปิด auto-update — `wp-config.php` โผล่ทีหลัง |

**ต้องมีทั้งคู่ ไม่ใช่เผื่อเหลือเผื่อขาด** — `path` unit เฝ้าโฟลเดอร์ `vhost/nginx/`
ซึ่งเปลี่ยนตอนสร้างไซต์ แต่ `wp-config.php` ไปโผล่**ข้างใน** `/www/wwwroot/<domain>/`
ซึ่งไม่ทำให้โฟลเดอร์ที่เฝ้าอยู่เปลี่ยน `path` unit จึงมองไม่เห็นเลย

### ทำไม systemd timer ทั้งที่ [05 §5.1b](05-operations.md) บอกให้ใช้หน้า Cron ของ panel

หน้า Cron ของ panel ชนะเรื่อง "ทีมมองเห็น" ซึ่งเป็นเหตุผลที่ `nightly-check.sh` ไปอยู่ที่นั่น
แต่เหตุผลนั้นพังเมื่อความถี่เป็นทุกนาที เพราะ panel เขียน log + เรียก `log_task_analyzer.py`
**ทุกรอบ** = 1440 entry ต่อวัน จนงานอื่นในหน้านั้นจมหาย — ของที่ใส่มาเพื่อให้มองเห็น
กลายเป็นของที่ทำให้มองไม่เห็น

`Type=oneshot` ของ systemd ยังกันรันซ้อนให้ในตัว ไม่ต้องพึ่ง `flock` แบบทาง B

> ข้อนี้**ไม่ขัด**กับกฎ "อย่าใช้ `systemctl` กับ service ของ aaPanel" ใน README
> กฎนั้นพูดถึง nginx/php-fpm/redis ซึ่ง aaPanel รันผ่าน `init.d` ทำให้ `systemctl`
> รายงานไม่ตรง — `wpaa-newsite` เป็น unit ของเราเอง ไม่มีของ init.d ให้ขัดกัน

### ทำไมไม่ใช้ `inotify-tools`

`systemd.path` ก็ใช้ inotify เหมือนกัน แต่มากับเครื่องอยู่แล้ว ไม่ต้อง `apt-get install`
ไม่ต้องเขียน daemon ค้างที่อาจตายเงียบ ๆ และได้ `Type=oneshot` กันรันซ้อนมาฟรี

### ทำไมไม่มีไฟล์จำสถานะ

ตัวเลือกที่ง่ายกว่าคือจำรายชื่อไซต์ที่ stamp ไปแล้วในไฟล์ แต่แบบนั้นจะพลาดทุกกรณีที่
ของถูกเขียนทับทีหลัง — ซึ่งบนเครื่องนี้เกิดจริงเป็นประจำ (WP Toolkit เขียนทับ config
ทุกครั้งที่เพิ่มไซต์) สคริปต์จึงอ่านจากของจริงทุกรอบว่า "ไซต์ไหนยังขาดอะไร"
ผลคือมันกู้ตัวเองได้ด้วย ไม่ใช่แค่จับของใหม่

### ความเสี่ยงเรื่อง FastCGI cache ที่เคยอ้าง — ตรวจแล้วไม่มีจริงบนเครื่องนี้

ตอนแรกเก็บข้อ "ยังต้องรัน `stamp-site.sh` เองอยู่ดี" ไว้ ด้วยเหตุผลว่าช่วงก่อน nginx reload
โดเมนใหม่จะไปหยิบเว็บของคนอื่นมาป้อน FastCGI cache แล้วค้างข้ามวัน (เคสจริงใน
[07 ข้อ 10–11](07-troubleshooting.md)) — **ตรวจของจริงแล้วเหตุผลนั้นตกไป** เพราะ
[ADR-011](#adr-011-catch-all-พอร์ต-443--return-404--cert-ของตัวเอง) ปิดไปก่อนหน้านี้แล้ว:

```
curl -sk --resolve nosuch.invalid:443:127.0.0.1 https://nosuch.invalid/   -> 404
grep -c fastcgi_pass /www/server/panel/vhost/nginx/0.catchall_ssl.conf    -> 0
```

catch-all `return 404` ตรงจาก nginx ไม่แตะ PHP เลย จึงป้อน FastCGI cache ไม่ได้
เคสในข้อ 10–11 เกิดตอนที่ยังไม่มี catch-all ต่างหาก ผลคือช่วงก่อน reload
คนที่เปิดโดเมนใหม่ได้ **404 ชั่วคราว** ไม่ใช่เว็บของลูกค้ารายอื่น และไม่มีอะไรค้าง

`watch-new-sites.sh` ยังสั่ง `clear-cache.sh <domain>` หลัง stamp อยู่ดี เป็นชั้นกันเผื่อ
วันที่ catch-all หลุดหาย ต้นทุนคือลบไฟล์ที่ KEY ตรงโดเมนนั้น ซึ่งไซต์ที่เพิ่งสร้างไม่มีของมีค่า

### ผลที่ตามมาที่ต้องรับ

- มี unit ของเราเองเพิ่ม 2 ตัวที่**ไม่โผล่ในหน้า panel** ทีมที่ดูแลต่อจะไม่เห็นจากหน้าจอ
  ต้องรู้ว่าให้ดูด้วย `systemctl status wpaa-newsite.path` — จึงเขียนไว้ใน
  [05 §5.1c](05-operations.md) และในสคริปต์ติดตั้งเอง
- `path` unit ตื่นทุกครั้งที่มีอะไรเปลี่ยนใน `vhost/nginx/` รวมถึงตอน panel ต่ออายุ SSL
  ซึ่งเขียน vhost ทับ — รอบพวกนั้นสคริปต์จะไม่เจออะไรให้แก้แล้วจบไปเงียบ ๆ ยอมรับได้
- ถ้า panel เขียน vhost **ก่อน** สร้างโฟลเดอร์ใน `/www/wwwroot/` รอบที่ `path` ปลุกจะยัง
  ไม่เห็นไซต์ แล้วต้องรอ `timer` อีกไม่เกิน 1 นาที (ลำดับที่สังเกตได้บนเครื่องนี้คือ
  โฟลเดอร์มาก่อน แต่ไม่ได้พึ่งลำดับนั้น)
